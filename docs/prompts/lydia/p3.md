# 3. SOURCE OF TRUTH — UC-44

Precondition:

Terdapat pengajuan pencairan dalam status **Dalam Proses**.

Alur resmi:

1. Admin membuka `Kelola Pencairan Dana`.
2. Sistem menampilkan antrean pengajuan penerbit.
3. Admin memverifikasi rekening dan riwayat penjualan.
4. Admin melakukan transfer sesuai nominal pengajuan.
5. Admin melanjutkan ke upload bukti transfer.
6. Setelah bukti berhasil diunggah, status menjadi `Selesai`.
7. Saldo dicatat sebagai telah dicairkan.
8. Sistem menampilkan:

**"Pencairan dana berhasil diselesaikan."**

Alternative:

Jika rekening tidak valid:

1. Admin memilih `Tolak Pencairan`.
2. Admin mengisi alasan.
3. Admin mengonfirmasi penolakan.
4. Status menjadi `Ditolak`.
5. Nominal dikembalikan ke saldo tersedia.
6. Notifikasi dikirim.

**Prompt 03 berakhir pada penyiapan transfer yang valid dan alur penolakan.**

Finalisasi status `Selesai` ditangani bersama UC-45 pada Prompt 04 agar bukti dan akuntansinya tidak terpisah.

# 4. FINANCIAL SOURCE OF TRUTH

Gunakan canonical ledger/reservation Dimas.

```
VERIFIED SALES
      |
      v
PUBLISHER EARNINGS
      |
      v
AVAILABLE BALANCE
      |
      v
PAYOUT REQUEST — Dimas
      |
      v
AMOUNT RESERVED
      |

      |
  +---+-------------------+
  |                       |
  v                       v
REJECT                 VALID REQUEST
  |                       |
  v                       v
RELEASE RESERVATION    EXTERNAL BANK TRANSFER
  |                       |
  v                       v
AVAILABLE BALANCE      TRANSFER CONFIRMATION
                          |
                          v
                  UPLOAD PROOF — UC-45
                          |
                          v
                       COMPLETED
```

Ini diagram domain, bukan nama tabel/status final.

## Critical rule

Dana yang sudah dipindahkan ke **Dalam Proses** oleh Dimas tidak boleh dianggap masih bebas untuk dicairkan ulang.

Jangan membuat administrator memotong available balance lagi ketika memulai proses.

Jangan melakukan double-debit.

# 5. BALANCE ACCOUNTING INVARIANTS

Bedakan:

- Pendapatan yang sah.
- Saldo tersedia.
- Dana yang direservasi dalam proses.
- Dana yang telah selesai dicairkan.
- Penyesuaian/refund jika kebijakan sudah tersedia.

## Example

```
Sebelum request:

Saldo Tersedia : Rp 1.000.000
Dalam Proses   : Rp 0
Telah Dicairkan: Rp 0

Dimas membuat request Rp 400.000:

Saldo Tersedia : Rp 600.000
Dalam Proses   : Rp 400.000

Jika Lydia menolak:

Saldo Tersedia : Rp 1.000.000
Dalam Proses   : Rp 0

Jika transfer sah dan selesai:

Saldo Tersedia : Rp 600.000
Dalam Proses   : Rp 0
Telah Dicairkan: Rp 400.000
```

Angka hanya contoh.

Jangan hardcode data tersebut.

## Important ledger semantics

UC-44 menyebut "memotong saldo secara permanen".

Jika dana sudah direservasi pada UC-36, langkah final bukan mengurangi saldo tersedia sekali lagi.

Langkah final adalah menyelesaikan reservasi menjadi pencairan yang telah dibayarkan.

Gunakan ledger contract yang ada.

Jika desain ledger berbeda, buktikan invariant saldo melalui tests.

Jangan membuat saldo negatif atau dua kali mengurangi uang yang sama.

# 8. REJECTION FLOW

UC-44 mengizinkan penolakan jika data rekening tidak valid.

## Required interaction

```
Klik Tolak Pencairan
         |
         v
Form Alasan Penolakan
         |
         v
Konfirmasi Penolakan
         |
         v
Backend Authorization
         |
         v
Atomic Status + Ledger Update
         |
         v
Status: Ditolak
         |
         v
Release Reserved Amount
         |
         v
Notify Publisher
```

## Validation

- Hanya admin berwenang.
- Request masih eligible untuk ditolak.
- Alasan wajib sesuai skenario.
- Alasan tidak boleh kosong/whitespace.
- Penolakan tidak boleh berlaku pada payout yang sudah benar-benar selesai ditransfer.
- Repeated action tidak menggandakan saldo.
- Penerbit yang sama boleh mempunyai pengajuan lain, jangan menyentuh pengajuan berbeda.
- Audit actor dan reason tercatat.

## Accounting

Penolakan harus atomik.

Status dan pelepasan reservasi harus berhasil bersama-sama.

Jika update ledger gagal:

- Status tidak boleh menjadi Ditolak tanpa saldo dipulihkan.
- Jangan mengirim notifikasi sukses.
- Lakukan rollback dan laporkan kegagalan.

# 9. MANUAL BANK TRANSFER WORKFLOW

Baseline arsitektur adalah transfer yang dilaksanakan oleh petugas melalui mekanisme perbankan resmi di luar aplikasi.

Aplikasi IKAPI **tidak otomatis mengirim dana**.

## Required distinction

Ada tiga peristiwa berbeda:

1. Pengajuan disetujui untuk diproses.
2. Transfer dana benar-benar telah dilakukan.
3. Bukti transfer berhasil diunggah dan pencairan difinalisasi.

Jangan menggabungkan ketiganya menjadi satu klik `Selesai`.

## Verification of transfer

Sebelum melanjutkan ke upload bukti:

- Admin memastikan transfer memang telah dilakukan melalui kanal bank yang sah.
- Nominal harus cocok.
- Rekening tujuan harus cocok dengan snapshot.
- Referensi transfer dicatat bila tersedia dan disetujui.
- Informasi tindakan dicatat untuk audit.

Jangan membuat dummy "Transfer Berhasil" karena admin menekan tombol frontend.

Jika belum ada transfer:

- Pengajuan tetap berada dalam workflow yang benar.
- Jangan membuat bukti palsu.
- Jangan mengurangi saldo dua kali.
- Jangan menampilkan status Selesai.

Jangan mengintegrasikan Midtrans Payouts tanpa keputusan resmi serta kesiapan merchant.

# 11. CONCURRENCY &amp; IDEMPOTENCY

Dua admin bisa membuka pengajuan yang sama.

Contoh:

```
Admin A memilih Tolak.
Admin B membuka pengajuan yang sama.

Admin A berhasil menolak.
Admin B mencoba menyelesaikan.
```

Hasil yang benar:

- Admin B tidak boleh menyelesaikan pengajuan yang sudah Ditolak.
- Tidak ada double ledger movement.
- Tidak ada stale state mutation.
- UI menampilkan status terbaru.

Gunakan:

- Database transaction.
- Row-level locking jika sesuai.
- Conditional status update.
- Unique ledger entry reference.
- Idempotent transition.
- Audit event.

Jangan hanya mengandalkan disabled button Filament.
