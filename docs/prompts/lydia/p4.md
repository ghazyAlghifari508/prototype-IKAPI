# 6. PRIVATE STORAGE

Bukti transfer berisi informasi finansial sensitif.

Gunakan storage privat.

### Required behavior

- File tidak disimpan di publicly accessible bucket.
- File tidak mempunyai permanent unauthenticated URL.
- Gunakan Laravel Storage abstraction.
- Storage path dibuat oleh sistem.
- Jangan mempercayai original filename untuk path.
- Gunakan file identifier/reference yang aman.
- Pastikan hubungan file dengan PayoutRequest.
- Jangan expose storage credentials.
- Jangan kirim private storage key ke Inertia/browser props.

Jika menggunakan local private disk:

- Jangan mengandalkan `storage:link` untuk membuka proof.

Jika menggunakan R2/S3:

- Gunakan bucket/object visibility private.
- Jika temporary URL digunakan, tetap patuhi authorization dan lifetime yang sesuai.
- Jangan membuat public ACL.

### Backend authorization

Penerbit hanya dapat mengakses proof miliknya melalui endpoint Aprila UC-37.

Admin hanya dapat mengunggah proof jika berwenang melakukan payout processing.

# 8. STORAGE &amp; DATABASE CONSISTENCY

Database transaction tidak otomatis melakukan rollback pada filesystem/object storage.

Karena itu, implementasi harus menjaga konsistensi keduanya.

Contoh failure:

```
Upload file berhasil.
Database update gagal.
```

Jangan meninggalkan file orphan tanpa cleanup/recovery.

Contoh lain:

```
Database mencatat payout Selesai.
Upload file ternyata gagal.
```

Ini tidak boleh terjadi.

## Safe finalization pattern

Rancang alur seperti:

1. Validasi request.
2. Validasi file.
3. Simpan file ke private storage.
4. Verifikasi storage operation berhasil.
5. Jalankan database transaction.
6. Lock/verify PayoutRequest status.
7. Pastikan transfer confirmation sah.
8. Kaitkan proof reference.
9. Finalisasi ledger reservation.
10. Update status menjadi Selesai.
11. Commit.
12. Dispatch notification after commit.

Jika transaksi database gagal:

- Pastikan status dan ledger rollback.
- Bersihkan atau tandai file staged yang belum sah.
- Jangan mengirim success notification.

Jika cleanup gagal, sediakan mekanisme recovery yang dapat ditelusuri.

Jangan mengasumsikan database transaction juga menghapus object storage.

# 10. CONCURRENCY &amp; IDEMPOTENCY

Kasus penting:

- Admin mengklik `Unggah Bukti` dua kali.
- Browser retry setelah timeout.
- Dua admin membuka payout yang sama.
- Satu admin sedang menolak sementara admin lain upload proof.
- Queue retry.
- Storage upload sukses tetapi response hilang.
- Payout sudah completed tetapi request upload lama datang belakangan.

Expected behavior:

- Hanya satu final completion yang sah.
- Ledger diposting tepat satu kali.
- Tidak ada duplicate proof aktif.
- Tidak ada completion notification ganda.
- Payout ditolak tidak dapat difinalisasi.
- Payout completed tidak dapat diproses ulang tanpa workflow yang jelas.
- Stale requests ditolak atau dikembalikan sebagai already processed dengan aman.

Gunakan database transaction dan locking/conditional transition sesuai schema.

Jangan mengandalkan disabled button saja.
