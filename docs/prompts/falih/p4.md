# 3. UC-07 — KOMENTAR BUKU

Skenario resmi:

1. Pengguna login.
2. Pengguna membuka detail buku.
3. Pengguna mengetik komentar.
4. Sistem memantau validitas input.
5. Tombol Kirim aktif hanya ketika teks layak dikirim.
6. Sistem menjalankan penyaringan konten.
7. Komentar yang lolos diproses dan disimpan.
8. Komentar terbaru ditampilkan.

Skenario secara khusus menyebut input yang hanya berupa spasi atau simbol tidak dianggap valid.

## Required behavior

- Komentar terhubung ke User dan Book.
- Pengguna harus login.
- Text validation dilakukan client dan server.
- Whitespace-only input ditolak.
- Input yang tidak memiliki konten bermakna ditangani.
- Panjang teks dibatasi sesuai kebutuhan.
- Konten berbahaya tidak dieksekusi sebagai HTML.
- Komentar baru muncul pada detail buku setelah penyimpanan berhasil.
- Error mempertahankan draft yang dapat diperbaiki.

Jangan membuat komentar palsu.

# 4. CONTENT FILTERING — UC-07

UC-07 menyebut "smart content filter".

Namun dokumen tidak menetapkan:

- Model AI khusus.
- Daftar kata terlarang final.
- Provider moderation.
- Confidence threshold.
- Bahasa yang harus didukung.
- Kebijakan false positive.
- Mekanisme banding.

**Jangan mengarang bahwa penyaringan konten harus menggunakan OpenAI API atau LLM.**

Audit apakah proyek telah mempunyai moderation policy atau rule set.

## Recommended implementation approach

1. Gunakan validation dan normalisasi input yang aman.
2. Gunakan aturan filter yang benar-benar telah disepakati.
3. Pisahkan content validation dari persistence.
4. Tangani spam dasar sesuai kebijakan, misalnya frekuensi pengiriman yang tidak wajar.
5. Gunakan rate limiting.
6. Simpan status moderasi yang diperlukan oleh kontrak administrator.
7. Berikan feedback yang dapat ditindaklanjuti.
8. Jangan menjanjikan filter sempurna.

Jika filter belum memiliki aturan resmi:

- Jangan membuat daftar kata kasar secara asal dan menyatakan itulah kebijakan IKAPI.
- Jangan mengklaim seluruh moderasi otomatis sudah selesai.
- Dokumentasikan konfigurasi/policy yang dibutuhkan.
- Sediakan arsitektur minimal yang dapat diperluas tanpa membuat framework moderasi besar.

## Rejected comment

Pesan sesuai skenario:

**"Komentar mengandung kata yang tidak pantas, mohon perbaiki ulasan Anda."**

Teks komentar harus tetap tersedia untuk diperbaiki.

Jika sistem dapat mengidentifikasi bagian yang melanggar aturan dengan cukup akurat, tampilkan penanda yang sesuai.

Jangan menandai kata secara spekulatif jika filter tidak mengetahui posisi pelanggaran secara pasti.

Jangan menampilkan alasan internal moderation engine yang sensitif.

# 5. UC-20 — ULASAN &amp; EVALUASI

UC-20 berbeda dari komentar biasa.

Precondition:

**Pengguna telah menyelesaikan pembelian buku terkait.**

Pengguna mengisi empat penilaian, masing-masing skala **1–5**:

1. Kesesuaian ekspektasi.
2. Kebermanfaatan isi.
3. Kesesuaian harga.
4. Peluang membeli lagi dari penerbit ini.

Pengguna juga menulis ulasan testimoni.

Kemudian menekan:

**Kirim Evaluasi &amp; Ulasan**

Backend memvalidasi seluruh jawaban, menyimpan hasil, dan memperbarui akumulasi evaluasi penerbit.

## Critical rule

Jangan mengizinkan evaluasi berstruktur hanya karena pengguna sudah login.

Verifikasi bahwa pengguna benar-benar mempunyai pembelian sah untuk buku tersebut, berdasarkan kontrak pembayaran yang telah diverifikasi backend.

Jangan gunakan status `paid` dari frontend.

Jangan gunakan localStorage untuk menentukan eligibility.

# 6. DATA MODEL — COMMENTS VS EVALUATIONS

Gunakan struktur yang konsisten tanpa menggandakan informasi.

```
Book
  |
  +-- General Comments (UC-07)
  |      |
  |      +-- Author User
  |      +-- Comment Text
  |      +-- Moderation State
  |
  +-- Evaluations (UC-20)
         |
         +-- Buyer User
         +-- Verified Purchase Reference
         +-- Expectation Score
         +-- Content Usefulness Score
         +-- Price Fairness Score
         +-- Repurchase Intention Score
         +-- Testimonial Text
         +-- Moderation/Visibility State
```

Ini ilustrasi domain.

Bila existing repository sudah memiliki shared Review model yang dapat menampung kedua jenis interaksi dengan aman, reuse.

Jangan memaksakan inheritance/polymorphism kompleks jika tabel sederhana lebih tepat.

Namun jangan membuat dua model identik untuk satu jenis komentar.

## Ownership

- Komentar terkait satu buku.
- Evaluasi terkait buku yang telah dibeli.
- Author berasal dari authenticated session.
- Penerbit tidak boleh berpura-pura menjadi pembeli.
- Rating tidak boleh berasal dari input administrator tanpa aturan.
- User tidak boleh mengubah `author_id` lewat request.
- Status moderasi tidak boleh ditentukan oleh frontend.

# 7. EVALUATION VALIDATION

Keempat aspek wajib diisi.

Validasi backend untuk setiap skor:

- Wajib.
- Integer.
- Minimum 1.
- Maksimum 5.

Jangan:

- Menggunakan decimal score.
- Menerima 0 atau 6.
- Menganggap nilai default 5 tanpa pilihan pengguna.
- Mengirim form kosong lalu menampilkan success.

Ulasan teks mengikuti requirement UC-20 dan aturan validasi yang disepakati.

Jika skenario mensyaratkan testimoni, pastikan field tidak kosong.

## Validation feedback

Ketika kuesioner belum lengkap:

**"Silakan lengkapi seluruh poin kuesioner evaluasi sebelum mengirim."**

Tampilkan field yang masih membutuhkan jawaban.

Jangan membuat modal error raksasa.

Jangan menghapus jawaban lain ketika satu field invalid.

# 9. AGGREGATION &amp; PUBLISHER METRICS

UC-20 menyebut pembaruan akumulasi rating performa penerbit.

Evaluasi mempunyai empat skor.

Jangan langsung menampilkan bintang 4.8 tanpa definisi perhitungan yang jelas.

## Data aggregation

Buat agregasi yang konsisten berdasarkan skor tersimpan dan review yang eligible.

Pertimbangkan:

- Skala 1–5.
- Empat aspek.
- Jumlah evaluator.
- Status moderasi.
- Evaluasi buku yang termasuk penerbit terkait.
- Efek penghapusan/moderasi terhadap skor.

## Important ownership

Falih menyediakan data evaluasi dan agregasinya.

Dimas UC-31 menggunakannya pada dashboard.

Jangan membuat dashboard penerbit dalam tugas ini.

Vayola UC-06 menggunakan rating yang sah pada detail buku.

Jangan membuat halaman detail kedua.

## Avoid stale metrics

Jika agregasi dihitung ulang:

- Pastikan tidak ada double counting.
- Pastikan moderasi/review deletion tercermin.
- Hindari menyimpan agregat di banyak tabel tanpa strategi konsistensi.
- Gunakan query atau mekanisme cache yang sesuai kebutuhan.

Jangan membuat nilai rating final melalui perhitungan yang berbeda di frontend dan backend.
