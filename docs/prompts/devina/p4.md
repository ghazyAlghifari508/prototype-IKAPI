# 4. INVOICE DATA CONTRACT

Gunakan sumber data backend yang benar.

Representasi konseptual:

```
Authenticated Buyer
        |
        v
Paid Order
        |
        +-- Order Number
        +-- Transaction Information
        +-- Payment Verification State
        +-- Order Items
        |      |
        |      +-- Book Title Snapshot
        |      +-- Quantity
        |      +-- Unit Price Snapshot
        |      +-- Line Total
        |
        +-- Subtotal
        +-- Discount (if approved)
        +-- Payment Fee (if approved)
        +-- Final Paid Amount
        +-- Payment Timestamp
        |
        v
      Invoice PDF
```

Nama field tersebut hanya menggambarkan data yang dibutuhkan.

Gunakan field dari model aktual.

## 4.1 Snapshot order values

Invoice harus mencerminkan **transaksi saat pembelian terjadi**.

Jangan menggunakan harga buku terbaru sebagai pengganti harga saat order dibuat.

Contoh masalah yang harus dihindari:

- Buku dibeli seharga Rp45.000.
- Penerbit mengubah harga menjadi Rp60.000.
- Invoice lama berubah menjadi Rp60.000.

Itu salah.

Gunakan item snapshot/harga transaksi yang benar-benar tersimpan.

Jika model Order belum memiliki snapshot yang memadai, koordinasikan kebutuhan perubahan kontrak dengan Ghazy tanpa menduplikasi order model.

## 4.2 Payment status

Invoice pembelian hanya boleh dikeluarkan untuk order yang memenuhi status pembayaran sah menurut kontrak Ghazy.

Jangan hanya memeriksa:

`status === "success"`

jika enum/status aktual berbeda.

Verifikasi definisi status domain yang sudah disepakati.

Contoh konseptual:

```
Order Pending
    |
    v
Invoice download DENIED

Order Failed
    |
    v
Invoice download DENIED

Order Expired
    |
    v
Invoice download DENIED

Order Paid and Verified
    |
    v
Invoice download ALLOWED
```

Status dari frontend atau URL tidak boleh dijadikan dasar utama otorisasi.

## 4.3 Multi-publisher orders

IKAPI adalah marketplace multi-penerbit.

Periksa apakah order dapat berisi buku dari beberapa penerbit.

Jika demikian, invoice harus mengikuti struktur order dan transaksi sebenarnya.

Jangan menghilangkan item dari penerbit lain.

Jangan membuat satu PDF terpisah untuk setiap penerbit tanpa dasar spesifikasi.

Jangan mengarang aturan komisi, fee, atau pajak.

Data pembayaran pembeli tidak sama dengan laporan payout penerbit.

# 6. PDF GENERATION ARCHITECTURE

Periksa dependency existing.

Jika belum ada PDF renderer yang sesuai:

- Evaluasi library PHP/Laravel yang kompatibel dengan versi Laravel dan PHP aktual.
- Verifikasi dokumentasi resmi, pemeliharaan, lisensi, dan keterbatasan renderer.
- Pilih satu implementasi yang diperlukan saja.
- Hindari menambahkan beberapa engine PDF sekaligus.
- Jangan gunakan HTML-to-image screenshot sebagai cara utama mencetak invoice.
- Jangan menggunakan browser-side HTML print sebagai pengganti PDF server-generated yang diminta UC-22.

Dokumen dihasilkan server-side berdasarkan data yang telah diverifikasi.

## Example architecture

```
GET /orders/{order}/invoice
           |
           v
Authenticate Buyer
           |
           v
Authorize Order Ownership
           |
           v
Check Verified Paid State
           |
           v
Load Order + Snapshot Items
           |
           v
Render Invoice Document
           |
           v
Return PDF Download
```

Route hanyalah contoh konseptual.

Jangan membuat route kedua jika endpoint serupa sudah ada.

## Generation strategy

Evaluasi apakah invoice lebih tepat:

- Dibuat on demand.
- Dibuat saat settlement lalu disimpan privat.
- Dibuat sekali dengan caching yang aman.

Pilih berdasarkan kebutuhan aktual dan arsitektur yang tersedia.

Untuk invoice sederhana dengan volume belum besar, hindari sistem dokumen asynchronous kompleks jika tidak diperlukan.

Apapun strateginya, repeated downloads harus menghasilkan informasi transaksi yang konsisten.

# 8. SECURE DOWNLOAD

Endpoint invoice harus diperiksa server-side.

## Required checks

- Buyer authenticated.
- Buyer owns the order.
- Order exists.
- Payment settled/verified according to canonical state.
- Account access follows active-user policy.
- No insecure direct object reference.
- No access to invoice milik pengguna lain.

Jangan mempercayai user ID dari input frontend.

Jangan mengizinkan download hanya karena user mengetahui nomor order.

Gunakan Policy/Gate sesuai arsitektur Laravel.

## Storage and response

Jika file PDF disimpan:

- Gunakan private storage.
- Jangan meletakkan invoice sensitif di direktori publik tanpa proteksi.
- Gunakan authorized download route atau signed temporary access sesuai desain.
- Pastikan filename aman.
- Pastikan file tidak diakses melalui path traversal.

Jangan menggabungkan filesystem path mentah dari query parameter.

Jika PDF dibuat on demand:

- Return response dengan content type yang benar.
- Gunakan attachment filename yang wajar.
- Tangani generation failure.
