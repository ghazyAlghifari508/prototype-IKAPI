# 3. CRITICAL DOMAIN MODEL DISTINCTION

**Publisher approval berbeda dari account activation.**

Jangan menggunakan satu kolom `status` yang maknanya berubah-ubah untuk kedua konsep jika struktur existing tidak mengharuskannya.

Representasi konseptual:

```
USER ACCOUNT
  |
  +-- Account Access Status
  |      |
  |      +-- active
  |      +-- suspended
  |
  +-- Business Role
  |      |
  |      +-- buyer
  |      +-- publisher
  |      +-- administrator
  |
  +-- Publisher Application (if applicable)
         |
         +-- pending
         +-- approved
         +-- rejected
```

Nama status merupakan contoh; gunakan kontrak aktual dari codebase.

**Contoh penting:**

Penerbit dengan:

- Approval `approved`.
- Account `suspended`.

Tidak boleh mengakses portal penerbit.

Penerbit dengan:

- Approval `pending`.
- Account `active`.

Tetap tidak boleh mengakses portal penerbit karena approval belum selesai.

Aktivasi ulang akun `suspended` tidak berarti menyetujui permohonan penerbit yang masih pending/rejected.

Jangan mencampurkan dua state machine tersebut.

# 6. SUSPEND ACTION

Ketika admin menonaktifkan akun:

1. Recheck actor authorization.
2. Re-query target record.
3. Periksa status terkini.
4. Pastikan transisi diperbolehkan.
5. Minta alasan yang relevan.
6. Simpan perubahan.
7. Catat audit.
8. Kirim notifikasi.
9. Pastikan access restriction efektif.

Alur:

```
Admin pilih Nonaktifkan
          |
          v
Konfirmasi + Alasan
          |
          v
Server Authorization & Validation
          |
          v
Persist Status + Audit
          |
          v
Notify User
          |
          v
User Tidak Bisa Mengakses Area Terproteksi
```

## Important rules

Jangan menghapus User record.

Jangan menghapus:

- Order.
- Invoice.
- Buku yang dibeli.
- Bookmark.
- Profil.
- Riwayat transaksi.

Penonaktifan tidak sama dengan penghapusan data.

Jangan otomatis mengubah pembayaran yang telah sukses menjadi gagal.

Jangan otomatis mencabut hak kepemilikan e-book secara permanen hanya karena akses akun sedang ditangguhkan.

Data tetap utuh dan akses aplikasi mengikuti status akun.

# 7. REACTIVATION ACTION

Ketika admin mengaktifkan kembali akun:

- Recheck permission.
- Recheck target state.
- Pastikan tindakan sesuai kebijakan.
- Simpan perubahan.
- Catat actor dan timestamp.
- Kirim pemberitahuan.
- Jangan memberi role baru.
- Jangan mengubah publisher approval.
- Jangan mengubah histori transaksi.

Contoh:

```
Publisher:
Approval = pending
Account  = suspended

Admin reactivates account

Approval = pending
Account  = active

Publisher portal access remains denied.
```

Ini wajib diuji.

## Existing sessions

Pertimbangkan pengguna yang sudah login sebelum disuspend.

Perubahan status harus berlaku pada request yang relevan berikutnya.

Jangan hanya memeriksa status saat login pertama.

Gunakan mekanisme middleware/policy yang tepat.

Untuk protected actions, verifikasi account status dari sumber tepercaya.

### Avoid accidental lockout

Jangan membuat mekanisme yang membuat pengguna suspended:

- Tidak bisa logout.
- Tidak bisa melihat informasi penonaktifan apabila kebijakan mengizinkan.
- Terjebak redirect loop antara login dan dashboard.

Buat UX yang jelas dan aman untuk penolakan akses.

### Cross-role integration

Pastikan:

- Buyer suspended tidak dapat menjalankan checkout.
- Publisher suspended tidak dapat mengelola buku.
- Admin panel tetap membutuhkan izin admin yang benar.
- Approval publisher tetap berlaku secara independen.

Jangan mengimplementasikan checkout, manajemen buku, atau admin role management hanya untuk pengujian status akun.
