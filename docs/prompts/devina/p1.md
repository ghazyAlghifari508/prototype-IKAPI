# 5. ADMIN IDENTITY &amp; AUTHORIZATION

## 5.1 Single User model

Aplikasi IKAPI menggunakan satu sistem identitas pengguna.

Administrator tetap menggunakan User model yang sama.

Jangan membuat:

```
users
admins
admin_users
```

sebagai tiga sistem login berbeda.

Jika tidak ada kebutuhan arsitektural yang terverifikasi, tetap gunakan:

```
users
  |
  +-- Roles
  |
  +-- Permissions
  |
  +-- Filament Panel Access
```

## 5.2 Explicit authorization

Akses panel harus memiliki syarat yang dapat diverifikasi.

Current baseline:

- Authenticated user.
- Verified email.
- Permission `access-admin-panel`.
- Correct Filament panel ID.

Pertahankan baseline tersebut.

Jika repository hasil Prompt Fadli sudah menetapkan role admin:

- Verifikasi naming role.
- Verifikasi permission mapping.
- Pastikan role tidak otomatis diberikan ke user publik.
- Pertahankan permission-based panel access.
- Jangan membuat role dengan makna sama tetapi nama berbeda.

## 5.3 Role vs permission

Jangan mengasumsikan:

`role = admin`

selalu otomatis memberikan akses panel tanpa memeriksa permission.

Ikuti strategi otorisasi yang sudah ditetapkan.

Jika role administrator dipakai untuk mengelompokkan permission, assignment harus dilakukan melalui proses tepercaya.

Jangan menerima role atau permission dari request registrasi publik.

## 5.4 No local authorization bypass

Akses administrator harus aman di:

- Local.
- Testing.
- Staging.
- Production.

Jangan menggunakan logika:

```
if (app()->environment('local')) {
    return true;
}
```

untuk memberikan akses admin.

Jangan memberi izin pada semua akun terverifikasi.

Jangan memberi akses berdasarkan suffix email yang tidak disepakati sebagai sumber otorisasi.

# 6. ADMIN ACCOUNT PROVISIONING

Repository pada snapshot yang diperiksa belum memiliki seeder akun administrator default.

Ini perlu diperhatikan.

## 6.1 Objective

Pastikan tim mempunyai proses yang aman dan terdokumentasi untuk menyiapkan akun administrator yang sah.

Namun:

**Jangan membuat akun administrator default menggunakan kredensial hardcoded.**

Dilarang:

- Email/password admin yang ditulis langsung di source code.
- Seeder yang selalu membuat akun admin dengan password tetap.
- Credentials yang ditampilkan di laporan.
- Public registration yang mempunyai pilihan role admin.
- Endpoint publik untuk menaikkan privilege.
- Hidden frontend control untuk mengubah user menjadi admin.
- Auto-grant permission pada semua akun yang login.

## 6.2 Recommended provisioning approach

Audit terlebih dahulu apakah repository memiliki proses provisioning admin.

Jika sudah tersedia:

- Gunakan.
- Verifikasi keamanan dan idempotency.
- Dokumentasikan prosedurnya.

Jika belum tersedia:

- Sediakan prosedur operasional yang aman untuk membuat/menetapkan administrator melalui mekanisme tepercaya.
- Gunakan role dan permission existing.
- Pastikan hanya operator berwenang yang dapat menjalankan proses tersebut.
- Hindari hardcoded credentials.
- Hindari otomatis membuat administrator pada setiap deployment.
- Hindari mengubah data akun lain tanpa otorisasi.
- Pastikan tidak ada jalur privilege escalation dari aplikasi publik.

Buat command khusus hanya bila memang diperlukan dan tidak ada mekanisme framework/proyek yang memadai.

Jangan membangun sistem manajemen administrator lengkap untuk satu operasi provisioning.

## 6.3 Initial admin

Periksa kebutuhan administrator pertama.

Bedakan:

- Membuat User.
- Memverifikasi email.
- Memberikan izin akses admin.
- Mengakses dashboard.

Tidak semua langkah harus terjadi melalui route publik.

Dokumentasikan alur yang benar-benar diimplementasikan.

## 6.4 Permission registration

Jika permission `access-admin-panel` belum disiapkan melalui mekanisme provisioning:

- Periksa existing seeder.
- Gunakan guard yang sesuai.
- Gunakan proses idempotent.
- Hindari duplicate permissions.
- Jangan menghapus permission existing.
- Jangan memberikan izin admin kepada buyer/publisher.

Pastikan fresh database dan database yang sudah berisi user tetap dapat ditangani secara aman.

# 7. LOGIN ADMINISTRATOR — FUNCTIONAL REQUIREMENTS

## 7.1 Login form

Gunakan halaman login Filament yang sudah ada.

Form minimal:

```
IKAPI JAWA BARAT

Masuk Administrator

Email
[................................]

Kata Sandi
[................................]

[Masuk Administrator]
```

Tidak perlu membangun halaman React hanya untuk mendapatkan desain tersebut.

Sesuaikan branding/login presentation melalui extension mechanism Filament yang resmi jika diperlukan.

## 7.2 Validation

Pastikan:

- Email wajib.
- Password wajib.
- Format input masuk akal.
- Invalid login ditolak.
- Tidak ada kredensial di URL.
- Tidak ada password di logs.
- Tidak ada pesan yang membocorkan detail sensitif.

## 7.3 Invalid credentials

Ketika email/password tidak sesuai:

- Tidak membuat sesi admin.
- Menampilkan pesan yang jelas.
- Mengosongkan password input sesuai UC-39.
- Memungkinkan pengguna mencoba kembali.
- Tidak mengungkap apakah email terdaftar.

Pesan yang dapat dipakai:

**"Email atau kata sandi salah, atau Anda tidak memiliki akses administrator."**

Pastikan pesan mengikuti mekanisme keamanan Filament.

Jangan menambahkan logic yang membocorkan apakah suatu email memiliki permission admin.

## 7.4 Unauthorized authenticated user

Pengguna dengan password benar belum tentu administrator.

Contoh:

- Buyer valid.
- Publisher valid.
- Publisher pending.
- User tanpa permission admin.

Mereka tidak boleh mendapatkan akses `/admin`.

Pertahankan `canAccessPanel()` dan mekanisme auth middleware.

Jangan bergantung pada sembunyi/tampil menu frontend.

## 7.5 Successful login

Ketika berhasil:

- Session menggunakan Laravel/Filament.
- Pengguna diarahkan ke `/admin` atau route dashboard yang benar-benar tersedia.
- User memperoleh akses hanya ke resource yang diizinkan.
- Tidak ada permission baru yang diberikan melalui login.
- Login sukses tidak mengubah status approval, role, atau data lainnya.

UC-39 menjelaskan feedback "Login Berhasil".

Untuk UX aplikasi nyata, redirect langsung setelah login merupakan pendekatan yang sesuai jika tidak membutuhkan konfirmasi tambahan.

Tidak perlu membuat modal "Login Berhasil" dengan tombol OK hanya untuk meniru diagram langkah literal.

Jika feedback sukses tetap ditampilkan, gunakan mekanisme Filament yang ringkas dan tidak menduplikasi notifikasi.

Dokumentasikan perbedaan UX dari skenario jika ada.

# 10. SESSION MANAGEMENT &amp; LOGOUT

Pastikan login menggunakan mekanisme framework.

Periksa:

- Session driver.
- Authentication guard.
- Session regeneration.
- Remember-me jika tersedia.
- Logout.
- Session invalidation.
- CSRF protection.
- Rate limiting.

## 10.1 Logout

Ketika administrator logout:

- Session akses admin berakhir sesuai mekanisme Laravel/Filament.
- Pengguna tidak bisa mengakses protected page tanpa login kembali.
- Browser navigation tidak boleh menjadi jalur bypass authorization.
- Route dan resource tetap dilindungi oleh middleware.

Jangan membuat custom logout endpoint baru jika Filament sudah menanganinya.

## 10.2 Session and permission revocation

Jika permission administrator dicabut:

- Akses selanjutnya ke `/admin` harus ditolak.
- Sesi lama tidak boleh menjadi alasan untuk mengabaikan authorization terbaru.
- Cache permission perlu ditangani sesuai mekanisme Spatie apabila relevan.

Periksa apakah implementasi Filament yang terpasang mengevaluasi `canAccessPanel()` pada protected requests.

Jangan hanya mengecek akses saat login pertama.

# 11. ACCESS CONTROL &amp; SECURITY

UC-39 adalah fitur autentikasi administrator, sehingga pengujian keamanan merupakan bagian utama acceptance criteria.

## 11.1 Required security principles

- Server-side authentication.
- Password hashing dari Laravel.
- Session-based authentication.
- CSRF protection.
- Verified account requirement.
- Explicit administrator permission.
- Login throttling.
- Protected routes.
- No privilege escalation.
- No sensitive information leakage.
- No hardcoded admin accounts.
- No default admin passwords.
- No development authorization bypass.

## 11.2 Avoid unauthorized access

Periksa skenario:

```
Buyer Login
     |
     v
Open /admin
     |
     v
ACCESS DENIED
```

```
Publisher Login
     |
     v
Open /admin
     |
     v
ACCESS DENIED
```

```
Verified Admin + Valid Permission
     |
     v
Open /admin
     |
     v
ACCESS ALLOWED
```

```
Admin Permission Revoked
     |
     v
Open /admin Again
     |
     v
ACCESS DENIED
```

Jangan membuat user dapat memperoleh permission admin melalui manipulasi frontend, profile form, atau registration request.

## 11.3 Email verification

`User::canAccessPanel()` saat ini mensyaratkan email verified.

Pertahankan persyaratan tersebut.

Jangan:

- Menganggap semua akun admin otomatis terverifikasi.
- Mengubah `email_verified_at` melalui login.
- Menghapus verified check.
- Mengubah verification flow Fadli.

Jika akun admin hasil provisioning belum diverifikasi, proses provisioning harus menangani kondisi itu secara sah dan terdokumentasi.

Jangan menjadikan bypass security sebagai solusi.

## 11.4 Other panels

Pastikan izin administrator hanya berlaku pada panel yang dimaksud.

Jangan mengembalikan `true` untuk semua panel.

Jika nantinya terdapat panel penerbit terpisah, otorisasinya harus memiliki aturan sendiri.

Jangan membuat panel kedua dalam tugas ini.
