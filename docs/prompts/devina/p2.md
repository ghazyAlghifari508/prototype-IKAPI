# 4. DATA MODEL &amp; STATE CONTRACT

Audit terlebih dahulu status yang dibuat Fadli.

Jangan membuat dua sistem status pendaftaran.

Jika existing contract menggunakan:

```
pending
approved
rejected
```

pertahankan semantiknya.

Jika menggunakan enum/konstanta dengan naming berbeda, reuse existing naming.

Jangan mengubah status internal secara sepihak tanpa memeriksa dependensi login penerbit.

## State transition

```
                 PENDAFTARAN
                      |
                      v
                   PENDING
                      |
                +-----+------+
                |            |
                v            v
             APPROVED     REJECTED
                |            |
                v            v
          Akses portal    Akses portal
          diperbolehkan   ditolak
          sesuai policy
```

Aturan:

- Registrasi baru tidak otomatis approved.
- Approve hanya dilakukan aktor yang berwenang.
- Reject harus menyimpan alasan.
- Aksi tidak boleh memodifikasi role administrator.
- Repeated approval tidak boleh menggandakan log atau notifikasi tanpa alasan.
- Jangan otomatis menyetujui kembali pendaftaran rejected.
- Perubahan status harus mengikuti transisi yang diperbolehkan oleh domain.
- Jika kebijakan pengajuan ulang belum disepakati, jangan menciptakan workflow resubmission sendiri.

## Data approval

Minimal harus dapat diketahui:

- Permohonan/penerbit yang diperiksa.
- Status sebelum dan sesudah.
- Administrator pelaksana.
- Waktu tindakan.
- Alasan penolakan bila ada.

Gunakan struktur database yang konsisten dengan kode existing.

Jangan menyimpan data identitas penerbit dua kali.

# 6. APPROVE ACTION

Sebelum memproses:

1. Authenticated admin harus tersedia.
2. Permission untuk approval harus valid.
3. Record penerbit harus ditemukan.
4. Status saat ini harus diperiksa ulang dari database.
5. Transisi harus diperbolehkan.
6. Perubahan harus konsisten.

Gunakan transaksi database untuk status dan audit record yang harus atomik.

Jika approval berkaitan dengan role/permission:

- Gunakan mekanisme yang telah disepakati dengan Fadli.
- Jangan membuat role `publisher_active` kedua jika `publisher` sudah digunakan dengan pemeriksaan approval.
- Jangan mengganti status tanpa menjaga authorization contract.
- Jangan memberikan permission admin kepada penerbit.

## Prevent concurrent approval

Dua admin dapat membuka permohonan yang sama.

Pastikan aksi bersamaan tidak menyebabkan:

- Dua keputusan berbeda dianggap berhasil.
- Audit ambigu.
- Notifikasi ganda.
- Repeated role assignment tidak terkontrol.

Gunakan database transaction, row-level locking atau conditional update sesuai kebutuhan dan kemampuan struktur existing.

Jangan menganggap menyembunyikan tombol di UI cukup untuk mencegah race condition.

# 7. REJECT ACTION

Penolakan harus memerlukan alasan yang relevan.

Flow:

```
Administrator klik Tolak
          |
          v
Form alasan penolakan
          |
          v
Validasi alasan
          |
          +-- Tidak valid: tidak ada perubahan
          |
          v
Simpan keputusan + audit
          |
          v
Kirim notifikasi
```

Jangan menyimpan alasan kosong.

Jangan menggunakan alasan default palsu.

Jika terjadi error database, jangan mengirim email seolah keputusan sudah berhasil.

Jangan membatalkan akun User secara destruktif hanya karena pendaftaran ditolak.

Pastikan data diperlukan untuk audit tetap tersedia.

# 8. EMAIL NOTIFICATIONS

UC-40 mengharuskan pemberitahuan kepada penerbit.

Gunakan Laravel Notifications atau mekanisme yang sudah tersedia.

Notifikasi minimal:

**Approved**

- Identitas penerbit.
- Keputusan persetujuan.
- Informasi bahwa akses portal dapat digunakan sesuai persyaratan.
- Tautan ke login yang valid.

**Rejected**

- Identitas penerbit.
- Status penolakan.
- Alasan penolakan.
- Tidak menjanjikan pengajuan ulang jika fitur tersebut belum tersedia.

Gunakan bahasa Indonesia profesional.

## Reliable delivery

Jika notifikasi diproses asynchronous:

- Kirim setelah transaksi database berhasil commit.
- Hindari duplicate dispatch.
- Tangani kegagalan antrean.
- Catat status pengiriman apabila diperlukan oleh kebutuhan operasional.
- Jangan menjadikan SMTP error alasan untuk membatalkan perubahan database yang sudah commit tanpa desain konsistensi yang jelas.

Gunakan queue existing; jangan menambah provider email tanpa izin.

Jangan mengklaim email terkirim ke penerima jika hanya dites menggunakan notification fake.

Jangan membocorkan alasan penolakan kepada pengguna lain.
