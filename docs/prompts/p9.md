# 6. STRICT ANTI-AI-SLOP REQUIREMENTS

These rules are mandatory.

Do not generate:

- Giant shadows.
- Random decorative dots.
- Unnecessary status pills.
- Badges attached to every heading.
- Massive rounded containers.
- Gratuitous gradients.
- Decorative floating icons.
- Excessive cards.
- Generic analytics KPI panels.
- Repeated information.
- Fake urgency.
- Oversized page headings.
- Artificial loading indicators.
- Empty decorative panels.
- Unnecessary explanatory paragraphs.
- Icons beside every text label.
- Marketing slogans.

**Text-background rule:**

Ordinary headings, subtitles, and labels must not automatically receive separate white-background frames.

White surfaces should be used only where grouping or visual separation is justified.

**Copywriting rule:**

All user-facing text must use concise, natural Indonesian.

Bad:  
"Yuk, intip perjalanan transaksi literasimu!"

Good:  
"Riwayat Pembelian"

Bad:  
"Selamat! Petualangan bukumu sudah selesai dengan sempurna!"

Good:  
"Pesanan Selesai"

Bad:  
"Oops, riwayat belanjamu masih sepi nih!"

Good:  
"Belum ada riwayat pembelian."

Bad:  
"Yeay! Invoice berhasil disiapkan!"

Good:  
"Invoice siap diunduh."

Do not duplicate the same information in a heading, subtitle, badge, and card.

# 8. UC-16 — DIGITAL ORDER STATUS

Create the buyer's digital-order status experience.

Suggested frame:

`F07 / Order Status / Desktop`

## 8.1 Required information

Show:

- Order identifier.
- Order date.
- Relevant purchased book items.
- Total order amount.
- Current digital order status.
- Contextual next action.

Where relevant, indicate:

- Menunggu Pembayaran.
- Lunas.
- Selesai — Akses Buku Aktif.

## 8.2 Status presentation

Use restrained visual treatment.

For example:

**Menunggu Pembayaran**

"Pesanan menunggu penyelesaian pembayaran."

Action: **Lihat Pembayaran**

**Lunas**

"Pembayaran telah dikonfirmasi."

If book access is also confirmed, the interface may indicate that access is active.

**Selesai — Akses Buku Aktif**

"Buku tersedia di perpustakaan Anda."

Do not imply that the purchased books are available when access has not been confirmed.

## 8.3 Suggested desktop hierarchy

```
+--------------------------------------------------------------+
| EXISTING BUYER HEADER                                        |
+--------------------------------------------------------------+
|                                                              |
| Status Pesanan                                               |
|                                                              |
| +----------------------------------------------------------+ |
| | Pesanan IKAPI-DEMO-0001                                  | |
| | 05 Nov 2026                           Menunggu Pembayaran | |
| |----------------------------------------------------------| |
| | [Cover] Judul Buku A                                     | |
| | [Cover] Judul Buku B                                     | |
| |                                                          | |
| | Total Pesanan                         Rp XXX.XXX          | |
| |                                                          | |
| | [Lihat Pembayaran]                                      | |
| +----------------------------------------------------------+ |
|                                                              |
+--------------------------------------------------------------+
```

Adapt the hierarchy to existing design conventions.

Do not add an analytics dashboard around this information.

## 8.4 Required states

Represent:

1. Order awaiting payment.
2. Paid order.
3. Completed order with active book access.
4. Empty active-order state.

The empty-state wording should follow the specification:

"Belum ada pesanan digital yang sedang berjalan."

Provide a useful navigation path only where appropriate.

## 8.5 State logic

Pending orders should not display:

- Download invoice for a settled transaction.
- Active book ownership.
- A completed-purchase message.

Paid orders should not display:

- Unpaid instructions as the primary content.
- An expired payment code.
- A payment-required warning.

Do not fabricate unsupported fulfillment stages for physical goods.

No shipping, courier, package, or delivery-tracking UI.

Create the buyer's purchase-history experience.

## 9.1 Required content

Display previous transactions with:

- Order identifier.

- Relevant book information.
- Order total, where available.
- Transaction status.
- Clear detail action.

The use case explicitly requires transaction dates and statuses.

Additional fields should appear only when useful and consistent with approved data.

## 9.2 Desktop structure

A table or structured list is appropriate.

```
Riwayat Pembelian

+--------------------------------------------------------------+
| Tanggal     Pesanan          Buku          Total     Status  |
|--------------------------------------------------------------|
| 05 Nov      IKAPI-0001       Buku A        Rp ...    Lunas   |
| 03 Nov      IKAPI-0002       Buku B        Rp ...    Pending |
| 01 Nov      IKAPI-0003       Buku C        Rp ...    Lunas   |
+--------------------------------------------------------------+
```

Use appropriate column widths and readable text.

Avoid creating a separate card for every small data field.

## 9.3 Mobile structure

Do not compress a desktop table until it becomes unreadable.

Use responsive rows or compact transaction summaries.

Example:

```
05 November 2026
IKAPI-DEMO-0001

Buku A, Buku B
Rp XXX.XXX

Lunas              [Lihat Detail]
```

Keep the structure balanced and readable.

## 9.4 Interactions

Allow:

- Opening order details.
- Opening an invoice from an eligible paid order.
- Navigating to existing payment status when applicable.

Do not invent extensive filtering, sorting, or search features merely because typical order-history websites include them.

A restrained filter may be added only when justified by existing conventions and useful for demonstrating the history screen.

## 9.5 Empty history

Create the documented empty state:

**Riwayat Pembelian Kosong**

"Belum ada transaksi pembelian."

Optional contextual action:

**Jelajahi Buku**

Link it to the existing catalog if supported.

Avoid large decorative illustrations, generic slogans, and excessive card containers.

# 11. UC-22 — BUYER INVOICE

Create a professional purchase-invoice design.

Suggested frames:

- `F07 / Invoice / Preview`
- `F07 / Invoice / Download Error`

An invoice is an official-looking transaction document. Its content must be accurate and restrained.

## 11.1 Eligibility

The documented invoice download is available for **paid orders**.

Do not enable a completed invoice download for pending, cancelled, or expired transactions.

## 11.2 Required invoice information

Include:

- Relevant IKAPI marketplace identification.
- Invoice or transaction reference.
- Order identifier.
- Transaction date.
- Purchased book information.
- Quantity where applicable.
- Unit prices.
- Subtotal and approved adjustments.
- Final paid total.
- Appropriate payment status.

Use verified project mock data.

Do not fabricate:

- Business registration numbers.
- Tax identifiers.
- Official stamps.
- Signatures.
- Company addresses.
- Bank account details.
- Unapproved commission rates.

If the existing documents provide authorized institutional details, use them accurately.

## 11.3 Invoice layout reference

```
+----------------------------------------------------+
| IKAPI JAWA BARAT                                   |
| Invoice Pembelian                                  |
|                                                    |
| No. Invoice : INV-DEMO-0001                        |
| No. Pesanan : IKAPI-DEMO-0001                      |
| Tanggal     : 05 Nov 2026                         |
| Status      : Lunas                               |
|----------------------------------------------------|
| Buku                     Jumlah      Subtotal      |
|----------------------------------------------------|
| Buku A                      1        Rp ...        |
| Buku B                      1        Rp ...        |
|----------------------------------------------------|
| Subtotal                              Rp ...        |
| Penyesuaian yang disetujui            Rp ...        |
| Total Dibayar                         Rp ...        |
+----------------------------------------------------+
```

Treat this as a conceptual layout, not a mandatory design template.

## 11.4 Invoice presentation

The document should resemble a clean, readable PDF invoice.

Prioritize:

- Structured alignment.
- Clear financial totals.
- Consistent numbers.
- Readable typography.
- Adequate margins.
- Appropriate document proportions.

Avoid:

- Giant colored banners.
- Decorative success cards.
- Repeated green "Lunas" badges.
- Unnecessary gradients.
- Oversized logos.
- Tiny financial text.
- Unapproved official-looking seals.

## 11.5 Download interaction

Include a clear **Unduh Invoice PDF** action.

For the FigCraft prototype:

- Represent the action as a conceptual download.
- If the tool cannot attach a real PDF, do not claim a file was downloaded.
- Use a clearly labeled interaction or destination state if needed.

Do not generate real invoices through a backend.

Do not confuse the PDF invoice with the purchased e-book PDF.

**The invoice may be downloaded; this does not authorize downloading the original e-book.**

## 11.6 Download failure

Create the documented failure state.

Suggested message:

**Gagal mengunduh invoice.**

"Silakan coba beberapa saat lagi."

Action:

**Coba Lagi**

Use a coherent, compact error treatment.

Do not place an unrelated error toast beside a modal or outside the intended layout.

Do not show the failure and success states simultaneously.
