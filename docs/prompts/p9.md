`layouts.admin` dan partials P04. **Pertahankan shell Admin existing**: header ungu geometris dengan angled banner, sidebar kiri, content canvas putih, tab navigation, full-width tables; drawer detail berupa overlay dari kanan ketika ada action, bukan panel permanen yang membuat tabel sempit. ## 3. Routes dan komponen

Map tiap halaman unik menjadi `resources/views/admin/...` dan named routes dengan prefix `/admin/...` sesuai P01; IDs untuk row detail di frontend mock, jangan route `auth`/Admin middleware sebenarnya. Login Admin adalah UI/demo preview; jangan reuse login Breeze dan jangan menyebutnya aman/terlindungi. Gunakan shared table, status, modal/drawer components **hanya jika bentuknya benar-benar konsisten**. Hindari satu giant Admin Blade dengan hidden 9 views.

## 4. Interaksi per domain

- Dashboard: KPI/totals/alerts dari dummy fixtures konsisten.
- Kelola Pengguna: search, filter, detail drawer, status/role view demo, validation dan ownership according to source.
- Pengawasan Katalog: book records dan status berasal dari fixture yang sama dengan buyer/publisher; moderation action changes visible demo state when relevant.
- Moderasi Ulasan: report type `review` atau comment according source; jangan campur moderasi diskusi Komunitas.
- Monitoring Global: chart/cards/table state sesuai source dan shared fixture, no realtime fake network.
- Kelola Pencairan Dana: pending/approved/rejected simulation, related publisher finance shared state, no actual payout.
- Kelola Komunitas: admin-only simulated create/edit/visibility of communities, update Buyer Directory in same browser demo store.
- Moderasi Diskusi: report topic/reply target type + target ID, parent context of nested reply; status update consistent with buyer community thread. Jangan menghapus nested children ketika parent dimoderasi tanpa explicit policy.
- Login Administrator: demo role navigation with clearly limited mock access; no auth security claim.

## 5. Data consistency rules

One entity schema/source for user, book, publisher, order/payout, community, topic/reply/report; Admin displays derived read model from shared initial fixtures + browser state. Dummy metrics must derive from these where prototype relationship exists; if source has intentionally independent static KPI, document it as fixture instead of fabricating totals. Preserve unknown IDs and no silent fallback to first record.
