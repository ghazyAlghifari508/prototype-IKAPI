## 2. Urutan implementasi yang wajib

### A — Auth UI demo

Implementasikan layout auth dan halaman login, register, forgot password, verification, onboarding, serta konteks role Buyer/Publisher sesuai prototype. **Jangan** menyambung ke Laravel Auth, password hashing, email sender, OTP, database, atau middleware. Tombol demo boleh mengubah state lokal yang jelas, bukan mengklaim verifikasi nyata. Jangan mewarisi template Breeze. Untuk redirect auth versi mobile yang hanya alias, gunakan satu halaman responsive jika cocok baseline.

### B — Akun &amp; Pengaturan

Profile, dropdown, settings, status akun, bantuan. Gunakan satu demo session/role store; seluruh header/profile state tersinkron setelah navigasi/reload. Form validasi, inline error dan confirmation modal sesuai HTML. Tidak menyimpan kredensial sensitif atau mengklaim keamanan melalui localStorage. Jangan tambahkan input yang tidak ada di prototype.

### C — Cart &amp; Checkout simulasi

Cart item, subtotal, kupon/ongkir/biaya bila ada di HTML, payment selection, status success/pending/failed/expired yang memang ada, invoice preview dan riwayat order. **Tidak memanggil Midtrans**, tidak membuat webhook, tidak menyimpan transaksi sungguhan. State simulasi yang sama ditampilkan di cart, order history, dan library. Hindari 'checkout sukses' otomatis jika pilihan dan alur tidak mendukungnya.

### D — Perpustakaan, Ulasan, Web Reader

Library menampilkan buku demo yang sesuai alur order; reader tetap browser-only dan **tidak menyediakan unduh ebook** (sesuai keputusan produk). Periksa font, pagination, scroll, toolbar, zoom, theme, reading progress, chapter UI sesuai referensi. Jangan menciptakan warna krem atau palet baru. Review user state/empty/error harus mengikuti prototype.

### E — Agenda, detail agenda, bantuan, chatbot

Agenda Literasi tetap terpisah dari Komunitas; jangan membuat event section duplikat di Komunitas. Chatbot widget jika memang global harus dimuat sekali per shell yang membutuhkannya, tidak diduplikasi dan tidak mengirim request ke AI backend. Periksa `chatbot-widget.js` dan asset/font behavior. Jika tombol chat hanya demo, jangan sebut AI live.

## 3. Struktur

Contoh views: `auth-demo/*`, `buyer/account/*`, `buyer/checkout/*`, `buyer/orders/*`, `buyer/library/*`, `buyer/reader/*`, `buyer/agenda/*`, `buyer/help/*`; shared JS per domain `resources/js/ikapi/{auth-demo,checkout,reader,agenda,chatbot}/`. Gunakan P01 route mapping, named routes; gunakan `layouts.public` atau `layouts.auth` sesuai prototype. Jangan satu Blade giant dengan banyak view tersembunyi. Jangan copy paste JavaScript seisi HTML ke semua halaman.

## 4. State model frontend-only

- Fixture immutable untuk katalog, profil demo, agenda, order seed.
- Mutasi pengguna (wishlist/cart/order/reading progress/session/status) dikelola state JS yang eksplisit dengan namespace localStorage konsisten. Audit existing keys; migrasi non-destruktif bila perlu; jangan reset semua data.
- Handling same-origin dan multi-tab: sinkronisasi event storage bila diperlukan, jangan janji real-time multiuser. Tidak ada server-side auth; admin/publisher guard nanti cuma simulasi UI.
- Parse/validate setiap query parameter (`role`, `book`, `order`, `sesi`, dsb.) yang benar-benar dipakai; jangan fallback ke record pertama untuk ID tak dikenal.

## 5. Visual QA dan a11y

- Bandingkan source HTML dan Blade per subkelompok (A–E) pada viewport dari P02. Font, 2-column auth illustration, panels, header/account dropdown, checkout summary, reader typography, tab active, empty states, modal geometry harus identik.
- Form enter/tab/focus, disabled state, keyboard close modal, validation, CTA, browser back and reload. Scroll restoration pada reader dan checkout bila sesuai behavior source.
- Periksa Tailwind v4 classes dynamic JS dan loaded assets. Jangan menganggap hidden sections sebagai berhasil dirender.
