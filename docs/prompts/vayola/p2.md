# 5. SINGLE CATALOG QUERY

Pencarian dan filter harus memakai query katalog yang sama.

Jangan membuat:

- `SearchBooksController` dengan logika publikasi berbeda.
- `CategoryCatalogController` dengan query sendiri.
- Tiga salinan pagination.
- Search service yang tidak memakai public visibility rules.

Gunakan composable query dengan satu sumber visibility.

## Conceptual data flow

```
GET /books?q=...&category=...
                |
                v
       Validate Query Params
                |
                v
       Canonical Public Books
                |
         +------+------+
         |             |
         v             v
    Keyword Filter   Category Filter
         |             |
         +------+------+
                |
                v
        Stable Ordering
                |
                v
           Pagination
                |
                v
        Inertia Catalog Page
```

URL adalah ilustrasi.

Gunakan route naming dan slug/identifier existing.

## Search + category behavior

Contoh:

```
Keyword: "Laravel"
Category: "Teknologi"

Result:
Hanya buku dalam kategori Teknologi
yang cocok dengan keyword Laravel
pada field pencarian yang disetujui.
```

Jangan memperlakukan keyword dan kategori sebagai OR condition yang membuat kategori terabaikan.

Kedua kondisi harus dikombinasikan sesuai logika yang benar.

Jika keyword dihapus:

- Category tetap berlaku.

Jika category dihapus:

- Keyword tetap berlaku.

Jika keduanya dihapus:

- Kembali ke katalog umum.

# 6. URL-DRIVEN QUERY STATE

Gunakan URL query parameters sebagai state yang dapat dibagikan untuk search/filter/pagination.

Recommended behavior:

```
/books
/books?q=database
/books?category=teknologi
/books?q=database&category=teknologi
/books?q=database&category=teknologi&page=2
```

Ini contoh bentuk, bukan ketentuan nama param yang wajib ditiru jika codebase sudah mempunyai konvensi berbeda.

## Why URL state matters

- Hasil pencarian dapat dibagikan.
- Refresh tetap mempertahankan filter.
- Back/Forward browser tidak membingungkan.
- Pagination konsisten.
- Detail page dapat memiliki return context yang jelas.
- UI tidak perlu localStorage untuk menyimpan search state.

## Required interaction

1. User mengetik keyword.
2. User submit pencarian.
3. URL dan results berubah.
4. Input menampilkan keyword aktif.
5. User memilih kategori.
6. Results berubah dan keyword tetap ada.
7. User membuka page kedua.
8. Filter tetap dipertahankan.
9. User menghapus kategori.
10. Search tetap aktif.

Ketika keyword atau kategori berubah, reset page pagination ke awal agar user tidak tertinggal pada page lama yang tidak tersedia.

Jangan mengubah URL pada setiap keystroke tanpa kebutuhan; gunakan pola submit/debounce yang sesuai UI dan existing implementation.

UC-05 secara eksplisit menyebut tombol `Cari`. Pastikan submit search jelas.

# 7. BACKEND VALIDATION &amp; SECURITY

Validasi query parameters.

Perhatikan:

- Search string.
- Empty string.
- Whitespace-only input.
- Panjang keyword.
- Unicode/karakter bahasa Indonesia.
- Unknown category.
- Invalid page.
- Search/filter dari URL yang dimanipulasi.

Gunakan parameterized database queries.

Jangan memasukkan raw user input ke SQL string.

Jangan membuat dynamic `ORDER BY` atau raw SQL dari input client tanpa whitelist.

Jangan membocorkan unpublished books melalui search.

Jangan mengizinkan kategori yang tidak ada membuat internal SQL error.

## Publication visibility

Semua hasil wajib melalui canonical public book scope dari Prompt 01.

Tidak boleh terjadi:

- Katalog normal hanya menampilkan buku published.
- Tetapi pencarian menampilkan buku draft.
- Filter kategori memunculkan buku rejected.
- Keyword search memperlihatkan metadata private books.

Jangan menggandakan visibility logic; reuse.

# 8. POSTGRESQL SEARCH STRATEGY

Dokumen tech stack memilih:

**PostgreSQL Full-Text Search + pg_trgm** sebagai arah pencarian katalog.

Namun jangan langsung mengimplementasikan query kompleks tanpa melihat skema dan volume data aktual.

Lakukan:

1. Periksa query search existing.
2. Periksa jumlah data dan use case.
3. Identifikasi kebutuhan pencarian judul/penulis.
4. Periksa indexes.
5. Periksa dukungan PostgreSQL.
6. Pilih query strategy yang paling sesuai.
7. Tambahkan index hanya bila ada manfaat dan bukti yang jelas.
8. Dokumentasikan keputusan.

Untuk tahap awal, implementasi sederhana yang aman bisa memadai apabila performa sesuai.

Jika menggunakan full-text/trigram:

- Gunakan migration yang benar.
- Pertimbangkan PostgreSQL extension deployment.
- Tangani perbedaan pencarian bahasa secara benar.
- Uji ranking/relevance.
- Jangan mengasumsikan konfigurasi English FTS cocok untuk seluruh judul dan nama penulis Indonesia.

Jangan membuat Elasticsearch, Meilisearch, Algolia, atau vector database hanya untuk UC-05.

Jangan membuat AI search.

- Highest Rated.

terutama jika data dan rumusnya belum tersedia.
