# 4. CANONICAL DATA SOURCE

Gunakan model:

```
Authenticated Buyer
        |
        v
      Orders
        |
        +-- Order Number
        +-- Created Date
        +-- Payment Status
        +-- Order/Fulfillment Status
        +-- Total Amount
        |
        +-- OrderItems
        |       |
        |       +-- Book Title Snapshot
        |       +-- Quantity
        |       +-- Unit Price Snapshot
        |
        +-- PaymentAttempt/Transaction
```

Nama field adalah ilustrasi. Gunakan model aktual.

## Rules

- Semua query harus scoped ke authenticated user.
- Jangan menerima `buyer_id` frontend sebagai otoritas.
- Gunakan snapshot transaksi untuk histori.
- Jangan memakai harga katalog sekarang untuk transaksi lama.
- Jangan menyalin Order ke tabel history baru.
- Jangan membuat status pembayaran sendiri.
- Jangan menyamakan Paid dengan Entitlement Active.
- Jangan menyembunyikan pending/failed/expired/cancelled tanpa ketentuan yang jelas.
- Jangan menampilkan data transaksi pengguna lain.

## Multi-publisher orders

Satu order dapat berisi buku dari beberapa penerbit.

Riwayat pembeli harus mencerminkan satu checkout yang terjadi, bukan menggandakan entri karena ada dua publisher.

Jumlah buku dan nominal berasal dari order snapshot.

Jangan membuat satu row history per publisher jika domain menggunakan satu business order.

# 5. BACKEND QUERY &amp; PAGINATION

Gunakan Laravel Eloquent/Inertia.

Contoh route konseptual:

```
GET /orders/history
```

Nama route final mengikuti struktur existing.

Jangan membuat rute paralel apabila sudah ada.

## Query

- Authenticated buyer scope.
- Sort berdasarkan transaksi terbaru.
- Gunakan stable tie-breaker.
- Eager-load relasi yang diperlukan.
- Hindari N+1 queries.
- Projection hanya data yang dibutuhkan UI.
- Pagination server-side.
- Hindari mengirim seluruh riwayat transaksi dalam satu response.
- Jangan mengirim credential atau data sensitif payment provider.

Jika pagination sudah ada di shared components, reuse.

Jika ingin menambah filter status/periode, periksa apakah benar-benar diperlukan oleh current implementation. Jangan membuat sistem filter kompleks yang tidak diminta UC-17.

## Empty vs error

Bedakan:

- User benar-benar belum punya order.
- Query database gagal.
- Filter tidak menemukan hasil jika filter disediakan.

Jangan mengubah database error menjadi empty state yang menyesatkan.

# 6. STATUS PRESENTATION

Gunakan canonical statuses milik Ghazy.

Contoh tampilan yang harus dapat dibedakan:

- Menunggu Pembayaran.
- Lunas.
- Gagal.
- Dibatalkan.
- Kedaluwarsa.
- Hak Akses Buku Aktif.

Jangan menjadikan daftar itu instruksi membuat enum baru.

Gunakan status yang benar-benar tersedia.

## Status payment vs order

Contoh:

```
Pembayaran: Lunas
Akses Buku: Sedang Diproses
```

UI tidak boleh menyebut `Buku sudah tersedia` jika entitlement belum aktif.

Jangan mengambil status dari query parameter `success`.

Jangan memanggil Midtrans Get Status API untuk setiap row history tanpa kebutuhan.

Gunakan projection dari database yang sudah disinkronkan oleh domain Payment.
