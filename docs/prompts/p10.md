## 1. Full state inventory

Cari dan kelompokkan semua state/data existing yang dipakai di original HTML dan Blade baru:

- Demo Buyer/Publisher/Admin session + selected role (simulasi, bukan security).
- Publisher application `pending/approved/rejected` + status page.
- Books/categories/authors/publishers, catalog and detail.
- Cart, checkout choice, orders and statuses, library ownership/read progress.
- Ratings/reviews/report moderation, admin user/book status.
- Community membership, topic, root/nested reply with parentReplyId, discussion reports/moderation.
- Publisher sales/payout/account information, Admin payout/monitoring.
- Agenda, chatbot, other locally stored demo preferences.

Build a table `entity/state → source HTML keys → target store → consumers → mutators → consistency requirements`. **Do not delete or reset** saved demo state by default. Verify actual key names and shapes; names in conversation are examples only.

## 2. State ownership design

- Immutable initial fixtures may live in JSON/PHP arrays. Mutable actions must use **one explicit frontend demo store** per domain, not HTML-by-HTML duplicated copies.
- Prefer simple browser module with typed comments/interfaces or small validation functions over Redux-like architecture. Use explicit state version + idempotent migration to preserve existing localStorage. Treat invalid JSON/quota error gracefully.
- Cross-tab `storage` event only if relevant; one browser-origin environment. Browser session role flags are UI simulation only; never marketed as true access control.
- Distinguish server-rendered initial Blade data from browser state. Avoid stale Blade markup after navigating back/reload or duplicated on top of localStorage state.
- Preserve deterministic IDs/timestamps on existing records. When creating new demo entities, generate collision-resistant IDs appropriate for prototype; never use fixed IDs reused between submissions.
- Prevent invalid transitions (e.g. nonmember posting discussion, publisher pending accessing approved-only UI in demo, invalid order to library) only to the extent of the original prototype rules. Do not invent policy.

## 3. End-to-end scenario integration

Document and make functional within the same browser:

1. Guest → catalog → detail → cart → simulated login/checkout → order history → library → web reader.
2. Registration as Publisher → pending approval UI → Admin simulated approval → Publisher dashboard state; rejection case too if present.
3. Publisher book demo edit → Buyer catalog / Admin catalog visibility consistency where intended by prototype.
4. Buyer review/report → Admin moderation → Buyer review visibility if source supports.
5. Buyer community join → create topic → reply to specific comment → Admin discussion moderation → updated thread visibility. Preserve parent-child graph and deleted parent descendants.
6. Publisher payout request → Admin payout status → publisher finance view; no real transfer.
7. Browser refresh, Back/Forward, direct deep links, changing demo role (without hidden auto-login).

**Do not make features cross-sync that original prototype never linked unless a minimal shared fixture is needed for demonstrable correctness.** Clearly distinguish existing behavior preservation from optional proposed enhancement.

## 4. Routing and alias review

Audit all href/form action JS location redirects. Replace paths of `.html` with Laravel `route()`/URL helper in Blade; don't modify original HTML. For redirect-only prototype files, preserve alias behavior via named routes or safe redirects as approved P01. Handle invalid `?role=`, book ID, topic ID, reply ID, status IDs explicitly; never default to first entity. Check browser direct refresh and relative asset URLs.

## 5. UX preservation and diagnostics

This phase is **not** a UI redesign. Changes to DOM/CSS limited to resolving integration regressions. Keep modal focus and disabled state, icons, copy, radio/tab states, empty/loading/error. No network calls to business API or accidental form submit to default route; forms meant for mock actions must prevent unintended navigation and show correct simulated feedback.

## 6. Tests and failure modes

- Test storage empty, seeded, already existing legacy state, invalid JSON, refresh/back, two tabs if used, long content, conflicting roles.
- Test duplicated listener guard, missing script, stale route, asset 404, wrong counts, unsynced user/cart/community data, race double-submit and stale selected IDs.
- Use original HTML behavior as oracle and P02 baseline. Do focused end-to-end check of flows before P11 final QA; do not claim full-site final verification yet.
