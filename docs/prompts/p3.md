## OBJECTIVE

Refactor the visual rendering of nested replies so the conversation resembles the **clear parent-child connection pattern used in Threads**, without copying unrelated social-media features.

The current implementation already supports parent relationships but fails to communicate them visually.

Expected result:

- Root comments are clearly separated.
- Child comments appear directly beneath their parents.
- Connector lines visually join parent and child avatars.
- Sibling replies are distinct.
- Deep replies remain readable.
- Deleted-parent placeholders preserve conversational context.
- Reply navigation and actions still work.

**This task is primarily a rendering and layout refactor. Preserve existing data relationships.**

Do not assume random absolute positioning is the root cause.

The actual problem is the layout structure and connector placement.

## 3. REPLY TREE SEMANTICS

Before changing CSS, verify the data relationship.

Example:

```
Topic
│
├── Raka [RPL-101]
│   │
│   ├── Pembeli Demo [RPL-102]
│   │   parentReplyId = RPL-101
│   │
│   └── Nadia [RPL-103]
│       parentReplyId = RPL-101
│
└── Dina [RPL-104]
    parentReplyId = null
```

The UI must reflect these relationships exactly.

### Rules

- Root replies remain root replies.
- Child replies remain attached to the correct parent.
- Siblings do not appear as descendants of each other.
- Sorting is stable and predictable.
- All visible reply IDs render at most once.
- No invented relationship based on screen position.
- No parent-child relationship based on text content.
- No accidental reordering when a user adds a reply.

Do not modify parent IDs merely to make the UI appear correct.

## 4. CONNECTOR-LINE ARCHITECTURE

### Important

Do not implement the entire conversation with nested `border-left` blocks.

Use a layout that understands:

- Avatar position.
- Parent row.
- Child container.
- Connector segment.
- Sibling order.
- Last-child termination.

### Preferred technique

Use CSS Grid or a similarly robust layout with explicit:

1. Avatar rail.
2. Comment content.
3. Child thread container.

For example:

```
┌─────────────┬──────────────────────────────────┐
│ AVATAR RAIL │ COMMENT CONTENT                  │
├─────────────┼──────────────────────────────────┤
│ Avatar      │ Author · Time                    │
│  │          │ Body                             │
│  │          │ Actions                          │
│  │          │                                  │
│  └──────────┼── Child avatar + content         │
└─────────────┴──────────────────────────────────┘
```

This is structural guidance, not a requirement to draw visible table borders.

### Connector requirements

- Vertical connector begins below the parent avatar.
- Connector extends toward the child.
- Rounded elbow turns toward the child avatar.
- Connector is subtle neutral gray.
- Connector does not overlap text.
- Connector does not pass through avatars.
- Connector does not extend below the last relevant child.
- Multiple siblings remain connected to the correct parent.
- Removed parents keep an appropriate connection to surviving children.

### Implementation options

Prefer CSS pseudo-elements or simple borders attached to meaningful structural wrappers.

If SVG is necessary for reliable geometry, keep it minimal and reusable.

Do not calculate arbitrary pixel coordinates for every reply using JavaScript.

Do not use fixed absolute coordinates that only look correct for one comment length.

## 5. SIBLING REPLIES

This case needs explicit attention.

Example:

```
[R] Raka
    Menurutku membagi bacaan per bab lebih mudah.

    Balas
    │
    ├── [N] Nadia
    │       Setuju, terutama untuk buku panjang.
    │
    └── [P] Pembeli Demo
            Aku justru lebih suka target harian.
```

### Requirements

- Both replies belong to Raka.
- Nadia is not visually the parent of Pembeli Demo.
- Connector has correct branch geometry.
- The final branch terminates cleanly.
- Siblings share consistent alignment.
- No accidental divider inserted between parent and child.

Root-level replies may have subtle separators.

Nested siblings should be grouped using spacing and connector lines rather than full-width article dividers.

## 6. DEEP NESTED REPLIES

Support deeper data relationships without making the layout unreadable.

### Desktop

Allow a limited number of visible indentation levels, usually 2–3.

### Mobile

Use shallower indentation, usually 1–2 visual levels.

These are design limits, not maximum database depths.

### When nesting exceeds the visual limit

- Preserve actual parentReplyId.
- Keep reply order and target correct.
- Avoid continuing to shrink the content width.
- Show a concise **Membalas [Nama Pengguna]** context when helpful.
- Keep the reply subpage available for following deeper conversations.
- Never flatten or rewrite parent IDs.

### Critical mobile rule

A deeply nested conversation must not become a 70px-wide text column.

Use a readable minimum content width without horizontal overflow.

## 7. AVATAR &amp; CONTENT ALIGNMENT

Currently the reply component uses an avatar and separate text container, but nested layout positioning needs refinement.

### Required

- Avatars remain consistent size per level.
- Avatar rail has predictable width.
- Name aligns with avatar.
- Timestamp is visually secondary.
- Body follows author metadata.
- Action controls belong to their comment.
- Long text wraps without extending beneath unrelated avatars.
- Nested avatars remain aligned with connector elbows.

### Do not introduce

- Large initials banners.
- Card-style avatars.
- Decorative circle backgrounds around every action.
- Unnecessary colored reply levels.

Small fallback avatars with initials are acceptable for individual demo users when there are no profile images.

The rejected large monogram problem applied to community cover imagery, not necessarily small user avatar fallbacks.

## 8. REPLY ACTION ROW

Preserve each reply's existing actions.

- Balas.
- Owner edit.
- Owner delete.
- Report where permitted.

### Preferred placement

Keep the action row in a predictable location immediately associated with the comment.

Do not let the Balas control float far to the right while the comment itself occupies a different column.

Use consistent spacing and touch-target sizes.

### Interaction

Click Balas on any reply:

1. Read exact reply ID.
2. Open its dedicated Reply page.
3. Display selected parent.
4. Write a response.
5. Store parentReplyId.
6. Return to the correct Topic Detail.
7. Display the new reply under the correct parent.

Do not replace this flow with an inline composer.

Do not scroll to the root-reply textarea.

## 9. NEW REPLY VISIBILITY

After publishing a child reply:

- Return to the correct topic.
- Render updated tree.
- Position the viewport reasonably near the new reply.
- Optionally use a subtle temporary emphasis for orientation.
- Do not permanently highlight the reply.
- Do not move it to the end as a root comment.
- Do not duplicate it.
- Do not change its parent.

If the same topic is later reloaded, the nesting should remain identical.

### Root-reply composer

The existing **Tulis Balasan** form at the bottom remains for responding directly to the topic.

Do not remove it.

### Child-reply composer

The dedicated Balas Komentar page remains the only way to respond directly to another reply.

Do not mix the two composers.

## 10. DELETED PARENT HANDLING

Existing data model preserves removed replies in the graph so their active descendants remain attached.

Retain that behavior.

Example:

```
Komentar telah dihapus
│
└── [P] Pembeli Demo
        Aku masih punya pertanyaan soal ini.
```

### Requirements

- Original removed body is not publicly visible.
- Child comments remain discoverable.
- Parent-child relationship stays consistent.
- Deleted placeholder does not expose private author information unnecessarily.
- Child actions still target their correct IDs.
- Reply counts reflect active visible replies.

Do not delete the entire subtree automatically when a parent is removed.

Do not silently promote children to root replies unless an explicit migration policy exists.

---

## 11. INVALID DATA SAFETY

Check for:

- Missing parent.
- Parent from another topic.
- Cyclic reply references.
- Duplicate IDs.
- Orphaned replies.
- Removed parent.
- Deep nesting.
- Long author names.
- Very long comment text.

Handle these without crashing or infinite recursion.

Do not silently assign an invalid reply to an unrelated parent.

Preserve data where possible.

Use a safe rendering fallback for invalid legacy data and report the anomaly.

Do not reset storage to hide inconsistencies.

---

## 12. PERFORMANCE

Avoid repeated full-tree reconstruction for every individual node.

Recommended:

1. Load all replies for current topic.
2. Build ID lookup.
3. Build children map.
4. Sort roots and children.
5. Render tree once.

If the existing architecture already does this correctly, reuse it.

Avoid:

- Repeated DOM queries inside deep recursive loops where unnecessary.
- Global re-render on every hover.
- Heavy animation libraries.
- Unbounded recursion without cycle protection.

Do not prematurely build virtual scrolling for a small prototype.
