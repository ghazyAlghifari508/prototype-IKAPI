# 3. VERIFIED USE CASE REQUIREMENTS

Sumber utama: `SCENARIO USE CASE_TERBARU.docx`.

## 3.1 UC-28 — Registrasi Akun Penerbit

Aktor: Penerbit.

Pengguna mengisi:

1. Nama penerbit.
2. Penanggung jawab.
3. Email.
4. Password.
5. Nomor telepon.
6. Alamat.
7. Nomor anggota IKAPI.

Pengguna menekan:

**Daftar sebagai Penerbit**

Sistem:

1. Memvalidasi data.
2. Menyimpan pendaftaran ke database.
3. Menetapkan status menunggu approval.
4. Menampilkan informasi bahwa pendaftaran berhasil dan sedang menunggu verifikasi administrator.
5. Mengarahkan pengguna ke halaman login portal penerbit.

Alternatif:

- Data belum lengkap.
- Email telah digunakan.
- Sistem menolak pendaftaran dan memberikan pesan kesalahan.
- Pengguna dapat memperbaiki form.

## 3.2 UC-29 — Login Akun Penerbit

Precondition:

**Akun telah disetujui oleh Administrator.**

Penerbit:

1. Mengisi email.
2. Mengisi password.
3. Menekan tombol **Masuk Portal Penerbit**.

Backend memeriksa:

- Kredensial.
- Keberadaan akun.
- Identitas akun penerbit.
- Status persetujuan akun.
- Status akses akun jika aturan tersebut sudah tersedia.

Jika valid dan disetujui, pengguna masuk ke portal penerbit.

Jika tidak:

- Login/akses ditolak sesuai status.
- Kesalahan ditampilkan.
- Password dibersihkan.
- Pengguna tetap dapat memperbaiki input.

## 3.3 Jangan mengubah makna use case

UC-28 bukan berarti pendaftaran langsung disetujui.

UC-29 bukan berarti semua pengguna yang memiliki password valid boleh masuk portal penerbit.

Jangan menerapkan approval hanya sebagai badge frontend.

Status persetujuan harus digunakan oleh otorisasi backend.

# 4. ARCHITECTURE — SINGLE USER IDENTITY

Repository menggunakan satu Laravel application.

Gunakan arsitektur existing:

```
Laravel Application
        |
        +-- Fortify Authentication
        |
        +-- User Identity
        |
        +-- Spatie Roles/Permissions
        |
        +-- Buyer Features
        |
        +-- Publisher Features
        |
        +-- Administrator/Filament
```

Jangan membuat sistem autentikasi paralel untuk penerbit.

## 4.1 Mandatory constraints

Jangan membuat:

- `publisher_users` sebagai sistem login terpisah.
- Tabel password kedua.
- Custom guard penerbit tanpa kebutuhan yang terverifikasi.
- JWT penerbit.
- Login API Node.js.
- Authentication berbasis localStorage.
- Session management custom.
- Auth token yang disimpan manual di frontend.
- Duplikasi tabel `users`.

Semua akun tetap menggunakan identitas User yang konsisten.

## 4.2 Separate identity from publisher data

Informasi akun pengguna berbeda dari informasi instansi penerbit.

Contoh pemisahan konseptual:

```
users
  |
  +-- ID
  +-- Name
  +-- Email
  +-- Password Hash
  +-- Phone (if shared)
  +-- Verification Data
  |
  v
publisher registration/profile data
  |
  +-- Publisher Name
  +-- Responsible Person
  +-- Address
  +-- IKAPI Member Number
  +-- Approval Status
```

Ini adalah gambaran domain, bukan skema SQL yang wajib ditiru mentah-mentah.

Audit ERD, model existing, dan kebutuhan UC-30 terlebih dahulu sebelum menentukan relasi final.

Gunakan struktur minimal yang:

- Normalized.
- Dapat dikembangkan.
- Memiliki ownership jelas.
- Tidak menduplikasi identitas User.
- Mendukung status persetujuan.
- Menjaga kompatibilitas migrasi.

### Ownership constraint

Fadli boleh membuat data pendaftaran yang **wajib** untuk UC-28.

Namun jangan sekaligus membuat seluruh publisher profile management milik Dimas (UC-30).

Jika data pendaftaran nantinya menjadi bagian profil penerbit, dokumentasikan struktur dan kontraknya sehingga Dimas dapat memperluas implementasi yang sama.

Jangan membuat dua tabel instansi penerbit dengan makna sama.

# 5. PUBLISHER REGISTRATION DATA MODEL

## 5.1 Minimum requirements

Data harus dapat menyimpan:

- User identity.
- Nama penerbit.
- Penanggung jawab.
- Kontak.
- Alamat.
- Nomor anggota IKAPI.
- Status persetujuan.

Gunakan foreign key dan relasi Eloquent yang sesuai.

## 5.2 Approval status

Minimal, sistem harus bisa membedakan:

- Pendaftaran belum disetujui.
- Pendaftaran sudah disetujui.

UC-40 juga mencakup penolakan dan penonaktifan akun.

Jika schema perlu mengakomodasi status tersebut, desainlah secara konsisten dengan dokumen, tanpa mengimplementasikan alur administratornya sekarang.

Contoh kemungkinan representasi:

```
pending
approved
rejected
```

Status akun nonaktif/suspended sebaiknya tetap dibedakan dari status permohonan registrasi jika domain existing memang memisahkan dua konsep tersebut.

**Jangan menganggap daftar status contoh sebagai skema final sebelum memeriksa dokumen dan implementasi.**

## 5.3 Default status

Registrasi penerbit baru harus menghasilkan:

`pending`

atau nilai internal setara yang telah disepakati.

Status ditetapkan oleh backend.

Jangan menerima status persetujuan dari payload pendaftaran publik.

## 5.4 Approval safety

Jangan memungkinkan request seperti:

```
approval_status=approved
role=admin
is_verified=true
```

untuk langsung mengubah hak akses pengguna.

Semua nilai persetujuan berasal dari proses tepercaya.

Tidak boleh ada jalur publik untuk menyetujui akun sendiri.

# 6. REGISTRATION BACKEND

## 6.1 Fortify integration

Periksa `app/Actions/Fortify/CreateNewUser.php` dan registration flow existing.

Perhatikan bahwa Fortify registration bawaan mungkin digunakan oleh pembeli.

Jangan mengubah satu action secara sembarangan sehingga registrasi pembeli ikut diwajibkan mengisi:

- Nama penerbit.
- Nomor anggota IKAPI.
- Penanggung jawab.
- Alamat instansi.

Bedakan use case registrasi pembeli dan penerbit dengan pendekatan yang sesuai arsitektur.

Gunakan kembali komponen/backend behavior yang layak digunakan bersama.

Jangan membuat sistem autentikasi paralel.

Jika diperlukan endpoint registration khusus penerbit, endpoint tersebut tetap harus menggunakan mekanisme User, hashing, validation, session, dan security dari aplikasi Laravel.

## 6.2 Atomic persistence

Bila registrasi melibatkan User serta data penerbit, pastikan tidak terjadi kondisi:

- User berhasil dibuat.
- Data penerbit gagal disimpan.
- Akun tertinggal tanpa data/role yang diperlukan.

Gunakan transaksi database untuk operasi yang harus konsisten.

Tangani kegagalan secara aman.

Jangan meninggalkan partial registration yang diam-diam dianggap berhasil.

## 6.3 Validation requirements

Backend wajib memvalidasi:

- Nama penerbit tidak kosong.
- Penanggung jawab tidak kosong.
- Email valid.
- Email unik sesuai kontrak identitas.
- Password sesuai aturan Fortify/project.
- Konfirmasi password cocok.
- Telepon memenuhi format yang disepakati.
- Alamat wajib.
- Nomor anggota IKAPI wajib.
- Input panjang/format dibatasi secara masuk akal berdasarkan kebutuhan nyata.

Untuk nomor anggota IKAPI:

**Jangan menciptakan aturan checksum, panjang nomor, ataupun format nomor resmi tanpa sumber yang dapat diverifikasi.**

Jika format resmi belum tersedia:

- Gunakan validasi keberadaan dan keamanan input yang masuk akal.
- Catat kebutuhan validasi resmi sebagai open issue.
- Jangan mengklaim nomor anggota telah diverifikasi secara institusional.

## 6.4 Duplicate registration

Pastikan:

- Email yang sudah terdaftar ditolak dengan benar.
- Constraint database mendukung keunikan email.
- Concurrent registrations tidak menghasilkan duplikasi akun.
- Nomor anggota tidak otomatis dianggap unik sebelum aturan bisnisnya dikonfirmasi.
- Form mempertahankan data non-password setelah validation failure.

Jangan mengubah constraint bisnis tanpa dasar.

# 7. PUBLISHER ACCESS &amp; ROLE

Ini salah satu bagian terpenting.

## 7.1 Identity vs authorization

Identitas penerbit dan hak mengakses portal merupakan dua konsep terkait tetapi berbeda.

Akun dapat memiliki identitas sebagai pendaftar penerbit, tetapi belum memiliki hak mengelola buku.

Representasikan perbedaan tersebut secara eksplisit.

## 7.2 Recommended access rules

```
Registered Publisher
        |
        v
Approval Status?
        |
  +-----+----------------+
  |                      |
  v                      v
PENDING                APPROVED
  |                      |
  v                      v
NO PORTAL ACCESS      Can authenticate
                         |
                         v
                    Authorized?
                         |
                         v
                    Publisher Portal
```

Pengguna dengan status pending tidak boleh mendapat hak publisher aktif.

Akun ditolak atau dinonaktifkan juga tidak boleh mendapatkan akses portal.

## 7.3 Spatie Permission integration

Gunakan sistem role dan permission yang sudah tersedia.

Periksa apakah Prompt 01 telah menetapkan role:

`buyer`

Untuk penerbit, gunakan konvensi yang kompatibel.

Nama internal yang dapat dipertimbangkan:

`publisher`

Tetapi jangan membuat duplikat role jika naming sudah disepakati di repository.

### Critical rule

**Role tidak boleh menjadi satu-satunya syarat untuk melewati approval.**

Hak akses portal harus mempertimbangkan status persetujuan yang valid.

Jangan menggunakan:

- Sekadar menyembunyikan tombol.
- Pengecekan role frontend.
- LocalStorage status.
- Status request yang dikirim sendiri oleh user.

Otorisasi harus ditegakkan server-side.

## 7.4 Pending/approved state lifecycle

Implementasikan pembatasan akses yang dapat dipakai oleh UC-40 nanti.

Jangan membuat approval UI admin dalam pekerjaan ini.

Jangan mengubah kode Filament untuk secara otomatis menyetujui semua penerbit.

Jika belum ada approval action yang valid, tes boleh mempersiapkan status approved secara eksplisit lewat factory/fixture terisolasi.

Namun jangan menambahkan public approve endpoint.

## 7.5 Protect all entry paths

Jangan hanya memeriksa approval ketika user submit form login penerbit.

Periksa juga akses langsung ke protected publisher routes.

Pertimbangkan:

- Browser refresh.
- Session yang sudah ada.
- Deep link.
- Status approval yang berubah setelah login.
- Akun yang dinonaktifkan.
- User pembeli yang mencoba mengakses portal.
- Pengguna admin yang tidak memiliki izin menjadi penerbit.

Jangan berasumsi bahwa sukses login otomatis berarti boleh masuk ke seluruh area penerbit.

# 8. UC-29 — PUBLISHER LOGIN

## 8.1 Login credentials

Input:

- Email.
- Password.

Tombol:

**Masuk Portal Penerbit**

Gunakan session authentication Laravel.

Jangan membuat custom password verification.

## 8.2 Login behavior

Pemeriksaan harus meliputi:

1. User ditemukan.
2. Password benar.
3. User memiliki identitas penerbit.
4. Status pendaftaran telah disetujui.
5. Akun tidak diblokir menurut aturan yang tersedia.
6. Portal authorization terpenuhi.

Jika seluruh syarat berhasil, pengguna dapat membuka portal.

Jika tidak, akses portal ditolak.

## 8.3 Error handling

Skenario UC-29 menggunakan pesan:

"Email/kata sandi salah atau akun Anda masih menunggu persetujuan Administrator."

Gunakan bahasa yang alami dan konsisten dengan UI.

Jangan membocorkan status suatu akun kepada pengguna yang belum membuktikan kepemilikan kredensial.

Untuk kredensial yang salah, gunakan pesan generik.

Untuk akun valid yang belum memperoleh approval, tampilkan penjelasan yang tepat tanpa membuka akses portal.

Contoh:

**Pendaftaran penerbit Anda masih menunggu persetujuan administrator IKAPI.**

Jangan menampilkan pesan sukses login untuk akun yang belum dapat mengakses portal.

## 8.4 Handling unauthenticated and pending sessions

Tentukan perilaku yang aman dan konsisten untuk:

- Invalid credentials.
- Pending approval.
- Approved account.
- Rejected registration.
- Suspended account.

Jangan membiarkan akun pending memakai authenticated session untuk mengakses resource publisher yang seharusnya terbatas.

Jika mekanisme autentikasi menghasilkan session terbatas sebelum approval, pembatasan tersebut harus ditegakkan dengan benar di setiap endpoint terkait.

Jangan menghapus session valid akun lain tanpa alasan.

## 8.5 Redirect

Setelah berhasil, gunakan route portal penerbit yang sebenarnya.

**Jangan mengarahkan ke** `/prototype/penerbit/dashboard`, karena itu bukan implementasi produksi.

Pada repository yang diperiksa, prototype lama telah dibersihkan dari `main`.

Jika dashboard penerbit produksi belum dibuat oleh Dimas:

- Jangan membangun dashboard lengkap.
- Jangan membuat dashboard palsu.
- Gunakan tujuan aman yang tersedia atau minimal access landing yang hanya menegaskan akses, jika benar-benar diperlukan untuk menguji autentikasi.
- Catat kontrak redirect final yang akan dihubungkan ke modul Dimas.

Jangan mengklaim portal Dimas sudah selesai apabila belum tersedia.
