Ikuti rekomendasi OWASP dan gunakan mekanisme Fortify yang sesuai.

Jangan sekadar mengganti teks frontend sementara respons backend masih membocorkan keberadaan akun.

# 10. ROLE &amp; APPROVAL CONSISTENCY

IKAPI memiliki beberapa peran.

Minimal:

- Pembeli.
- Penerbit.
- Administrator.

Password reset mengubah kredensial akun, **bukan otorisasi akun**.

## 10.1 Buyer

Setelah password reset:

- Identitas User tetap sama.
- Role buyer tetap sama.
- Data profil tetap sama.
- Order dan data terkait tidak berubah.
- Login dengan password baru bekerja.

## 10.2 Publisher

Setelah password reset:

- Identitas User tetap sama.
- Data pendaftaran penerbit tetap sama.
- Approval status tetap sama.
- Data instansi tetap sama.
- Akun pending tetap pending.
- Akun rejected tetap rejected.
- Akun approved tetap mengikuti authorization yang ada.

Jangan membuat reset password sebagai jalan pintas untuk melewati persetujuan Devina.

## 10.3 Administrator

Jika administrator menggunakan broker/User yang sama, pertahankan kemampuan reset password yang memang sah.

Namun:

- Jangan mengimplementasikan ulang login administrator.
- Jangan membuat approval workflow.
- Jangan memberikan akses Filament otomatis setelah reset.
- Permission `access-admin-panel` tetap harus diverifikasi.

## 10.4 Security boundary

Contoh yang tidak boleh terjadi:

```
Publisher Pending
        |
        v
Reset Password
        |
        v
Publisher Approved Automatically
```

Reset password tidak boleh mengubah role, approval, atau permission.
