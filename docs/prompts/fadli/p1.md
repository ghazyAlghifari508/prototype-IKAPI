# 5. UC-01 — REGISTRASI AKUN PEMBELI

## 5.1 Kebutuhan resmi

UC-01 menetapkan bahwa pengguna memasukkan:

- Nama.
- Email.
- Password.
- Nomor HP.

Sistem memvalidasi data dan menyimpan akun ke database.

Alternatif:

- Data tidak lengkap.
- Data tidak valid.
- Email sudah digunakan.

Gunakan kebutuhan tersebut sebagai dasar.

## 5.2 Existing implementation gap

Pada snapshot sebelumnya:

`resources/js/pages/auth/register.tsx`

memiliki:

- Name.
- Email.
- Password.
- Password confirmation.

Belum memiliki nomor HP.

`app/Actions/Fortify/CreateNewUser.php`

masih membuat User menggunakan:

- Name.
- Email.
- Password.

Migration `users` juga belum memiliki kolom nomor HP.

Karena itu, pekerjaan ini mencakup frontend, validation, migration, dan registration action.

## 5.3 Database changes

Periksa model dan migration aktual.

Jika nomor HP benar-benar belum tersedia, tambahkan melalui migration baru yang aman.

Jangan mengubah migration awal yang sudah dipakai pada environment tim jika migration penambahan kolom lebih tepat.

Gunakan tipe data string untuk nomor telepon.

Jangan menyimpan nomor HP sebagai integer.

Alasannya:

- Nomor dapat diawali angka nol.
- Nomor dapat memiliki kode negara.
- Nomor bukan nilai numerik untuk perhitungan.

Pastikan perubahan migration mempertimbangkan pengguna lama yang sudah ada.

Contoh pendekatan yang perlu dievaluasi:

- Kolom nullable pada database untuk kompatibilitas pengguna lama.
- Wajib diisi untuk registrasi pembeli baru melalui validasi backend.

Jangan langsung membuat constraint database yang merusak user lama.

Jangan memperkenalkan field bisnis lain seperti NPWP, rekening penerbit, alamat kantor, atau identitas badan usaha pada registrasi pembeli.

## 5.4 Validasi registrasi

Validasi wajib dilakukan di backend.

Pastikan:

- Nama wajib diisi.
- Email wajib dan memiliki format yang benar.
- Email unik.
- Nomor HP wajib untuk registrasi pembeli baru.
- Nomor HP memiliki validasi format yang sesuai.
- Password mengikuti aturan keamanan yang sudah ditetapkan.
- Password confirmation cocok.
- Input tidak valid ditolak.
- Password tidak pernah disimpan dalam bentuk plaintext.

Nomor HP harus mendukung format yang disepakati untuk pengguna Indonesia, dengan perlakuan konsisten terhadap bentuk lokal dan kode negara.

Jangan menambahkan batas panjang atau regex yang terlalu agresif tanpa dasar kebutuhan.

Gunakan error messages yang jelas dan berbahasa Indonesia.

Contoh:

`Email sudah terdaftar.`

`Masukkan nomor telepon yang valid.`

`Konfirmasi kata sandi tidak cocok.`

Jangan menggunakan pesan generik ketika field yang salah sudah diketahui.

## 5.5 Persistensi aman

Gunakan model User dan mekanisme Eloquent yang sudah ada.

Periksa:

- Mass assignment.
- Password hashing.
- Field casts.
- Unique email.
- Normalisasi email.
- Penanganan duplicate insert.
- Error validation.

Jangan menerima field `role`, `is_admin`, `permissions`, atau `email_verified_at` dari registrasi publik.

Jangan menggunakan payload form sebagai sumber kebenaran untuk hak akses.

# 6. FONDASI ROLE PEMBELI

Pekerjaan Fadli adalah salah satu dependensi penting bagi PIC berikutnya.

Saat pembeli mendaftar, sistem harus dapat mengenali bahwa akun tersebut adalah akun pembeli.

## 6.1 Existing implementation

`app/Models/User.php` sudah menggunakan:

`HasRoles`

melalui Spatie Permission.

Namun pada snapshot GitHub:

- Belum ada seeder role bisnis.
- Belum ada assignment role pembeli pada registration action.
- Registrasi standar belum membedakan jenis akun bisnis.
- Akses Filament memerlukan permission eksplisit `access-admin-panel`.

Gunakan fondasi tersebut.

## 6.2 Tanggung jawab pada prompt ini

Implementasikan **klasifikasi akun pembeli minimal** yang diperlukan oleh UC-01/UC-02.

Gunakan satu identitas User dan sistem role yang sudah ada.

Rekomendasi identitas internal:

`buyer`

Untuk label UI:

`Pembeli`

Periksa dulu apakah nama role sudah ditetapkan dalam source atau konfigurasi terbaru. Jika sudah ada konvensi resmi, ikuti konvensi tersebut.

Jangan memperkenalkan role alternatif yang memiliki makna sama.

## 6.3 Role initialization

Jika role `buyer` belum ada:

- Gunakan mekanisme seeding/provisioning yang sesuai untuk role dasar.
- Pastikan proses idempotent.
- Pastikan setup fresh database dapat dilakukan dengan prosedur yang terdokumentasi.
- Pastikan registration action tidak bergantung pada role yang secara diam-diam belum dibuat.
- Pastikan tes menginisialisasi role yang dibutuhkan secara terisolasi.

Jangan melakukan `findOrCreate` role secara berulang di setiap HTTP registration request sebagai pengganti proses provisioning yang benar.

Jangan menghapus role yang sudah ada.

## 6.4 Role assignment

Setelah registrasi berhasil:

- Akun baru memperoleh klasifikasi buyer yang benar.
- Tidak memperoleh role publisher.
- Tidak memperoleh role administrator.
- Tidak memperoleh permission sensitif.
- Tidak memperoleh akses Filament.

Gunakan assignment server-side.

Frontend tidak boleh menentukan role menggunakan nilai tersembunyi yang dianggap tepercaya.

Jika role assignment dan pembuatan user membutuhkan konsistensi transaksi database, pastikan kegagalan tidak meninggalkan akun parsial yang tidak dapat digunakan.

## 6.5 Security boundary

Pengguna publik tidak boleh dapat:

- Mengirim `role=admin`.
- Mengirim `is_admin=true`.
- Mengklaim akun sudah diverifikasi.
- Mendapat permission `access-admin-panel`.
- Mengubah status penerbit.
- Mengakses fitur administrator tanpa hak.

Jangan mengubah `User::canAccessPanel()` sehingga admin bisa masuk hanya karena berhasil login.

Pertahankan tes keamanan panel admin yang sudah ada.

## 11.1 Authentication

- Password diverifikasi server-side.
- Password disimpan dengan hashing aman.
- Login menggunakan session Laravel.
- CSRF protection tetap aktif.
- Session ID diregenerasi sesuai mekanisme autentikasi Laravel.
- Logout mengakhiri sesi dengan benar.
- Session tidak dikirim melalui localStorage.
- Login throttling tetap aktif.

## 11.2 Authorization

- Registrasi pembeli tidak memberikan permission admin.
- Role pembeli diberikan server-side.

- Tidak ada bypass berdasarkan environment local.

- Jangan menggunakan database produksi untuk testing.
- Jangan menghapus data pengguna existing.

## 11.4 Validation &amp; abuse protection

- Server-side validation wajib.
- Email uniqueness diterapkan.
- Login errors tidak membocorkan keberadaan akun.
- Rate limiting tetap tersedia.
- Validasi tidak hanya dilakukan frontend.
- Hindari double submission.
- Gunakan fitur keamanan framework sebelum membuat mekanisme custom.
