## Peran dan tujuan

Sebagai Senior Blade Component Architect, bangun **komponen UI berulang** yang mempertahankan HTML asli secara visual. Harus selesai setelah P03. Ini bukan migrasi seluruh halaman, bukan redesain header, dan bukan alasan untuk membuat mega-component.

## 1. Audit source layouts

Telusuri dan bandingkan HTML header/footer/shell di Pembeli, login/registrasi, Publisher, Admin. Dari source sebelumnya: public mempunyai header dua tingkat dengan search/nav, publisher dan admin mempunyai topbar, banner geometris ungu, sidebar. Jangan satukan shell yang berbeda hanya demi DRY. Ambil baseline dari P02.

## 2. Bentuk struktur semantik

Contoh target yang boleh disesuaikan:

```
resources/views/layouts/
  public.blade.php
  auth.blade.php
  publisher.blade.php
  admin.blade.php
resources/views/partials/
  public/header.blade.php
  public/footer.blade.php
  publisher/sidebar.blade.php
  publisher/topbar.blade.php
  admin/sidebar.blade.php
  admin/topbar.blade.php
resources/views/components/ikapi/
  book-card.blade.php
  community-card.blade.php
  form-field.blade.php
  modal.blade.php
  table-status.blade.php
```

Create only genuinely shared components with &gt;=2 real consumers or strong semantic reuse; explicit props/slots/variants. Avoid extracting minor wrappers, huge props spaghetti, or dependency on global `id` selectors.

## 3. Exact fidelity constraints

- Header: logo (same asset), search, cart count, login/register/account state (demo), primary nav, sticky height, mobile nav, focus/hover, borders, shadows, spacing, scrollbar. **No replacing it with generic navbar**.
- Auth shell: IKAPI illustration/panel/grid and existing role tabs; not Breeze.
- Publisher/Admin: preserve precise geometric purple banner, sidebar width and backdrop, responsive drawer/open/scrim behavior, nav active state, topbar notification UI and account area. Shared shell can use variants but must not leak publisher items into admin or vice versa.
- Footer: preserve content/link hierarchy and spacing, not a new footer design.
- Modal/drawer: correct focus, backdrop, escape/close, scroll lock, z-index, form state. Don't create multiple IDs when component repeats.
- Use `@extends/@section`, `@include`, and Blade components (`<x-ikapi...>`) where appropriate. Ensure no double `<html>/<head>/<body>`, duplicate fonts, Tailwind CDN, or duplicate JS listeners.

## 4. Route and JS hookup

Replace old `.html` anchors in shared navigation with named routes for pages **already present**; for future routes use a clearly documented route registry and avoid broken-looking active links. Keep aria-current and active link states derived from route name; do not hardcode an active item globally. Independent Blade pages must be navigable; preserve query params for community/topic/book.

## 5. Verification

- Create isolated showcase or test render for all four shells and key components; compare DOM/layout screenshot to source at 1440/390 widths with baseline.
- Check that Tailwind `@theme` classes compile, font loaded, image crop and nav sizes match.
- Check focus, keyboard, overlay stacking, expanded mobile sidebar.
- Do **not** migrate all feature pages in P04; only shared building blocks and smoke demonstrations.
