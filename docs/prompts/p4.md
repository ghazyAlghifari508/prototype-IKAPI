```
Discover a book

      ↓
Add to cart / continue purchase
      ↓
Review checkout
      ↓
Choose payment method
      ↓
```

## 2. E-book Reader

Confirmed requirement:

**Users cannot download purchased e-book files.**

Reading must take place through the application's web reader.

### Required design principles

- The reader belongs in the reading experience, not in a marketing section on the homepage.
- Users should understand which book they are reading.
- Provide clear reading navigation.
- Preserve reading-progress information if this is part of the specification.
- Support practical reading controls if required by the actual scope.
- Do not add a book-download button.
- Do not add an "Export PDF" action.
- Do not suggest downloading protected book content.
- Do not confuse invoice downloads with e-book downloads.

### Appropriate reader concept

```
┌──────────────────────────────────────────────┐
│ ← Perpustakaan Saya          Judul Buku       │
├──────────────────────────────────────────────┤
│                                              │
│             READING CONTENT                  │
│                                              │
│       Readable text and navigation           │
│                                              │
├──────────────────────────────────────────────┤
│ Previous        Reading progress      Next   │
└──────────────────────────────────────────────┘
```

This is an information hierarchy example, not a requirement to introduce unapproved controls.

Inspect the actual reader requirements before adding progress, bookmarks, notes, or reading settings.

### Reader copywriting

Use natural phrases when necessary:

- "Baca Buku"
- "Lanjut Membaca"
- "Kembali ke Perpustakaan"
- "Halaman Berikutnya"

Avoid technical or marketing copy such as:

- "Teknologi E-Reader IKAPI"
- "Auto-Resume Reader"
- "Baca di Browser Tanpa Unduh Berkas Asli"
- "PDF terlindungi, tidak diunduh"

Technical restrictions should not become decorative feature descriptions.

### Important

Do not design a fake e-reader screenshot and then present it as an implemented, functional reader.

If a screen is only a prototype, document that status accurately.

## 3. Checkout and Midtrans

Payment belongs in the transaction flow.

### Required checkout hierarchy

```
┌──────────────────────────────────────────┐
│ Checkout                                 │
├──────────────────────────────────────────┤
│ Ringkasan Pesanan                        │
│                                          │
│ Buku yang dibeli                         │
│ Total pembayaran                         │
│                                          │
│ [ Pilih Metode Pembayaran ]              │
└──────────────────────────────────────────┘
                  ↓
         Midtrans payment flow
                  ↓
            Payment status
                  ↓
        Purchased book access
```

Do not treat this diagram as an exact backend specification.

Inspect the product requirements and verified payment integration details.

### Mandatory constraints

- Do not recreate Midtrans Snap UI arbitrarily.
- Do not invent payment-channel availability.
- Do not fabricate virtual-account numbers.
- Do not fabricate QR payment data.
- Do not display a hardcoded payment-success state as if it were real.
- Do not invent payment expiration times.
- Do not claim that access is granted before confirmed payment if the specification requires verified status.
- Do not expose backend concepts such as webhooks to ordinary bookstore users without a meaningful reason.

If a real Midtrans Snap integration is eventually used, its integration and payment-state behavior must follow actual Midtrans documentation rather than a visually reconstructed mockup.

The prototype may represent the intended flow, but it must not falsely imply a real payment has occurred.

### Checkout copy

Prefer customer-facing language:

- "Ringkasan Pesanan"
- "Total Pembayaran"
- "Pilih Metode Pembayaran"
- "Menunggu Pembayaran"
- "Pembayaran Berhasil"
- "Pembayaran Gagal"

Use status messages only in their relevant states.

Do not display success and pending states simultaneously.

### Invoice vs. e-book

Invoice availability must follow verified application requirements.

If a downloadable invoice is supported, clearly label it "Unduh Invoice".

Never label an e-book download as an invoice.

Never add book-download actions.

## 4. Mobile Responsive Redesign

The supplied mobile screenshots reveal several areas needing improvement:

- The layout is very compressed.
- Important text appears unusually small.
- Navigation is dense.
- The homepage still contained irrelevant feature showcases.
- The reader demonstration and checkout mockup consume excessive mobile scrolling space.
- Product discovery is not sufficiently prioritized.

The mobile design should be intentionally composed, not merely a scaled-down desktop frame.

### Mobile header

Prioritize:

1. Brand identity.
2. Search.
3. Cart and account access.
4. Category and catalog navigation.

If all navigation items cannot fit, use an appropriate responsive navigation pattern.

Do not shrink text until everything fits on one row.

Do not let nav items become unreadable.

Do not display a fake dropdown arrow without a menu.

### Mobile hero

Recommended hierarchy:

```
┌─────────────────────────────┐
│ IKAPI Store       Cart/Menu │
├─────────────────────────────┤
│ Search books...             │
├─────────────────────────────┤
│                             │
│ Temukan bacaan              │
│ berikutnya.                 │
│                             │
│ Short description           │
│                             │
│ [ Jelajahi Katalog ]        │
│                             │
│  Meaningful book artwork    │
│                             │
└─────────────────────────────┘
```

Required:

- Strong readable headline.
- Clear action.
- Attractive, uncropped artwork.
- Sensible vertical spacing.
- No cramped multi-column desktop layout.
- No oversized decorative badges.
- No unnecessary paragraphs.

The precise ordering of hero art and CTA can be adapted to the image and viewport.

### Mobile categories

Use a pattern appropriate to the actual number of categories.

Options include:

- Two-column category list.
- Compact category navigation.
- Horizontal browsing when the interaction is clearly discoverable.

Do not force five columns into a narrow mobile screen.

Do not show unverified catalog counts.

### Mobile products

Display covers at a comfortable size.

Determine whether one or two products per row works best for the actual viewport and text lengths.

Use the real book-cover aspect ratio.

Do not clip product titles or buttons.

Ensure price and primary action remain understandable.

### Mobile events

Use a readable layout.

Do not squeeze three desktop event columns into a narrow viewport.

Preserve the visual importance of titles and relevant event information.

### Mobile footer

Group links clearly.

Avoid extremely small text and dense multi-column layouts.

Keep the footer consistent with the desktop identity.

## 7. FigCraft MCP Workflow and Efficiency

Use a disciplined inspection and editing process.

The following capabilities are documented in FigCraft MCP, but confirm their availability in the connected runtime:

- `inspect_document`
- `get_node`
- `screenshot`
- `run_command`
- `batch`

Recommended workflow:

1. Read the relevant active frame structure.
2. Inspect target components and existing prototype links.
3. Identify the smallest group of necessary changes.
4. Apply related edits together where supported.
5. Inspect the changed document.
6. Capture a screenshot of the changed frame.
7. Compare against the approved reference and task requirements.
8. Fix actual defects.
9. Continue to the next frame.

Avoid:

- Recreating the entire document repeatedly.
- Duplicating the same components unnecessarily.
- Re-inspecting unrelated layers.
- Creating placeholder frames to fill missing flows.
- Running identical failed operations without inspecting their effects.
- Repeating large visual redesigns without a clear defect list.
- Adding extra UI simply to demonstrate technical features.

If a tool reports an ambiguous failure, inspect whether changes were already applied before retrying.

- Responsive behavior.
- Meaningful interactions.
- Accurate metadata.
