## 1. Peran dan hasil yang harus diwujudkan

Bertindak sebagai **Senior Product Designer, Design System Architect, dan UI/UX Designer untuk marketplace e-book multi-penerbit**. Kamu bekerja melalui Claude Code dan Figma MCP untuk membuat **native editable Figma Design layers**, bukan screenshot, mockup HTML, kode React, atau laporan konseptual.

Konteks produk: IKAPI Jawa Barat Online Bookstore memiliki pengalaman pembeli, penerbit, dan administrator. Pada fase sebelumnya fondasi desain bergaya Notion sudah ditargetkan untuk pembeli. Fase ini harus membuktikan bahwa fondasi tersebut **bisa diperluas ke layar operasional yang lebih padat data** tanpa membuat design system kedua.

Hasil utama:

1. **F12 — Publisher Dashboard & Sales**: dashboard performa, daftar pesanan masuk, dan interaksi desain untuk akses invoice penjualan, termasuk state penting.
2. **Administrator Master Layout**: sidebar/topbar/layout utama yang reusable untuk area administrator, dengan contoh halaman administrasi pengguna dan katalog global sebagai *master screens*; siapkan tempat navigasi untuk area event/berita tanpa mengarang fungsi CRUD yang belum disepakati.
3. **Design-system extension yang diperlukan saja**: sidebar, data table, chart treatment, filter, metric presentation, status, row actions, dialogs dan detail panels apabila dibutuhkan layar nyata.
4. **Figma prototype links** pada alur representatif yang benar-benar bisa dibuat dengan tool tersedia.
5. **Audit anti-slop**, data yang masuk akal dan konsisten, layer rapi, komponen asli, serta laporan verifikasi.

**Jangan berhenti pada penulisan rencana.** Jika Figma MCP dapat menulis pada canvas dan file tujuan dapat diakses, kerjakan desain secara nyata sampai tuntas untuk cakupan ini.

## 6. Prinsip visual: Notion-inspired dengan kebutuhan dashboard yang realistis

Pertahankan bahasa visual Phase 01, yang bersumber dari Notion Style Reference:

| Peran | Nilai acuan | Penggunaan |
|---|---|---|
| Page canvas | `#F6F5F4` | Background lembut |
| Surfaces | `#FFFFFF` | Content panels, table surfaces |
| Primary action | `#0075DE` | Tindakan utama pada konteks yang tepat |
| Text | `#000000` / variasi alpha | Hierarki teks |
| Muted text | `#615D59`, `#757575` | Metadata dan teks sekunder |
| Border | `rgba(0,0,0,0.08)` | Dividers/surface separation |
| Selected surface | `#E6F3FE` | State terpilih yang subtle |
| Accent | `#FFB110`, `#F64932`, `#62AEF0`, `#02093A` | Jarang, sesuai fungsi |

Aturan:
- Pakai variables/text styles yang **sudah ada**. Jika shade status diperlukan, tambahkan semantic role yang jelas (success, warning, danger) dengan kontras memadai; jangan menciptakan palet admin terpisah.
- Inter dapat menjadi substitusi NotionInter jika sesuai aset/font yang tersedia. Jangan mengasumsikan font proprietary tersedia.
- Base spacing 4 px; dominan 8, 12, 16, 24, 32; ukuran font UI padat namun terbaca, umumnya 14–16 px.
- Radius kartu sekitar 12 px, tombol sekitar 8 px, kontrol kecil seperlunya. Hindari semua elemen berbentuk pil.
- Border halus lebih utama daripada shadow. Overlay boleh menggunakan shadow tipis bila membantu pemisahan.
- Admin/penerbit lebih information-dense daripada Beranda Pembeli; **jangan meng-copy hero besar atau card marketing ke dashboard**.
- Jangan menambah ilustrasi karakter, blob, glow, gradient, ornamental dots, atau decorative charts.
- Utamakan navigasi yang jelas, data yang relevan, tables yang terbaca, dan ruang putih yang proporsional.

## 7. Reuse existing components + necessary extensions

### Audit sebelum membuat komponen baru

1. Inventaris components/variants existing dari Phase 01.
2. Catat primitive yang bisa langsung dipakai: Button, Input, Search, Dropdown, Typography, Surface, Icon, Empty State, dsb.
3. Buat mapping: kebutuhan F12/Admin → komponen existing → varian tambahan yang dibutuhkan.
4. Gunakan component **instances** pada screens baru, bukan menggambar ulang secara visual.
5. Jangan melakukan rename/rename massal komponen existing jika akan memutus instance atau menciptakan kebingungan.

### Komponen tambahan yang diperbolehkan bila digunakan

- `Navigation/Publisher/Sidebar`, `Navigation/Admin/Sidebar` (gunakan shared shell dan content variants jika memang cocok).
- `PageHeader/Operational`, `Toolbar/Table`, `Breadcrumb` hanya bila hierarki membutuhkan.
- `Metric/Operational` dengan label/value/context, tidak memakai chart palsu dalam setiap card.
- `DataTable/Header`, `DataTable/Row`, `DataTable/Cell`, `DataTable/Empty` serta responsive mobile row treatment.
- `Status/Text` atau `Status/Indicator` jika semantik butuh status; **bukan badge dekoratif di semua sel**.
- `Filter/DateRange`, `Filter/Status`, `Search/Table`, `Pagination` bila memang membantu tugas utama.
- `Chart/SalesTrend` sebagai komposisi native layer/editable, bukan gambar screenshot.
- `Review/DetailPanel`, `Dialog/Confirm`, `Dialog/RejectionReason`, `Feedback/SuccessError` sesuai specimen admin.
- `Invoice/Action` dan invoice error treatment untuk UC-35.

States/variants yang perlu ditunjukkan secara **proporsional**: default, hover, focus, disabled, selected, empty, error, confirmation, dan success bila relevan. Jangan menggambar semua kombinasi yang tidak pernah dipakai.

**Quality gate:** component set harus memiliki kegunaan nyata dan digunakan sebagai instance pada minimal satu screen. Hindari 100 komponen dekoratif hanya untuk terlihat kompleks.

## 8. Data demonstration — realistis, koheren, dan jelas berstatus mock

Gunakan **data simulasi terstruktur** untuk desain Figma. Jangan mengklaim angka sebagai data transaksi IKAPI yang sebenarnya.

### Konsistensi data yang wajib

- Semua nilai Rupiah memakai format `Rp` yang konsisten dan tidak menggunakan angka tak masuk akal.
- `Jumlah buku aktif`, `Buku terjual`, `Pendapatan bersih`, `Saldo tersedia` harus konsisten dengan tabel/grafik demo yang diperlihatkan.
- Jumlah order yang terlihat dan total summary harus bisa dijelaskan (misalnya *recent orders* hanya subset dari periode, bukan total seluruh transaksi).
- `Pendapatan bersih` dan `Saldo tersedia` tidak otomatis sama; jangan mengarang aturan platform fee/komisi/pajak. Jika perlu menjelaskan selisihnya, labeli sebagai data demo dan catat asumsi.
- Data order penerbit harus berupa **penjualan buku milik penerbit**, bukan gabungan semua penerbit tanpa alasan.
- Buku/cover yang sudah digunakan di F03, bila dipakai kembali, **harus sama ID, judul, penulis/penerbit, dan sampulnya**.
- Status invoice hanya untuk pesanan yang sesuai dengan skenario (lunas); jangan memperlihatkan tombol download aktif pada pesanan yang belum dapat diterbitkan invoicenya.
- Akun pengguna, penerbit, dan buku dalam admin master adalah **data demo**, bukan data publik nyata yang seolah sudah diverifikasi.
- Tidak mengarang nama penerbit resmi atau identitas asli orang apabila tidak punya sumber tepercaya. Gunakan contoh fiktif yang jelas untuk prototyping.
- Jangan memakai teks `Lorem ipsum`, angka `9999+`, rating `5.0` untuk semua hal, atau fake trend tanpa periode dan label.

### State data

Siapkan data representatif untuk:
- Dashboard dengan aktivitas penjualan.
- Dashboard tanpa aktivitas (metrik `0`, chart empty yang jujur).
- Pesanan masuk dengan beberapa record yang berbeda tetapi konsisten.
- Pesanan kosong.
- Permohonan penerbit menunggu verifikasi + akun aktif/nonaktif (master admin).
- Buku global aktif/dilaporkan/dinonaktifkan jika memang digunakan dalam specimen moderation.

Semua angka yang ditampilkan harus diberi konteks tanggal/periode bila diperlukan; tidak perlu badge besar `DATA DEMO` di setiap card. Satu catatan demo yang jelas pada halaman canvas atau handoff cukup.

## 9. F12 — Publisher Dashboard (UC-31)

### Tujuan dan isi wajib

Tampilkan dashboard penerbit yang membantu pengguna menjawab:
- Berapa banyak buku aktif?
- Berapa buku yang terjual?
- Berapa pendapatan bersih dan saldo tersedia?
- Bagaimana tren penjualan dalam periode yang ditampilkan?
- Apa transaksi terbaru dan bagaimana evaluasi pembeli jika memang relevan?

Berdasarkan skenario UC-31, tampilkan empat metrik utama yang spesifik:

1. **Buku Aktif**.
2. **Buku Terjual**.
3. **Pendapatan Bersih**.
4. **Saldo Tersedia**.

Jangan membuat tambahan KPI seperti “Growth Momentum”, “Engagement Power”, atau “Active Community” hanya untuk mengisi layar.

### Struktur desktop yang disarankan

```text
+--------------------------------------------------------------------+
| Publisher sidebar | Header: Dashboard Penerbit / period context    |
|                   |------------------------------------------------|
|                   | Buku Aktif | Buku Terjual | Pendapatan | Saldo  |
|                   |------------------------------------------------|
|                   | Tren Penjualan (chart dengan axis & periode)   |
|                   |------------------------------------------------|
|                   | Transaksi Terbaru | Evaluasi Pembeli (if valid) |
+--------------------------------------------------------------------+
```

Diagram adalah arah struktur, bukan keharusan menaruh semua elemen dalam kotak terpisah. Layout harus nyaman dibaca dan tidak padat hanya demi terlihat kompleks.

### Grafik penjualan

- Chart harus relevan dan mempunyai satuan yang jelas (jumlah buku terjual atau nilai Rp sesuai spesifikasi dan label).
- Gunakan skala, label sumbu/titik waktu, dan legend bila ada lebih dari satu seri; jangan chart tanpa label yang hanya menjadi ornamen.
- Gunakan native Figma shapes/vectors yang editable, bukan screenshot chart, gambar dari internet, atau kompleksitas visual yang tidak perlu.
- Tidak perlu interaksi chart advanced jika Figma prototype tidak mendukungnya. Cukup tunjukkan periode/representasi yang jelas.
- Jika menampilkan perubahan periode, siapkan contoh frame/state yang konsisten; jangan membuat ilusi filter bekerja tanpa link/state.

### Evaluasi pembeli

Skenario menyebut skor evaluasi kepuasan. Tampilkan ringkasan **hanya jika indikator yang dipakai dapat dijelaskan dari spesifikasi**. Bila tidak ada formula/pembobotan, jangan menciptakan “Customer Happiness 98%”. Ringkasan ulasan/rating demo yang jelas sumber dan konteksnya bisa digunakan secara hati-hati, atau catat kebutuhan keputusan.

### Empty state

Buat state tanpa penjualan: empat metrik bernilai nol, chart memiliki pesan yang jelas seperti `Belum ada data penjualan`, dan daftar transaksi tidak diisi secara palsu. Sidebar dan struktur halaman tetap konsisten.

### Responsive

- Desktop utama 1440 px.
- Mobile utama 390 px.
- Di mobile, navigasi menjadi pola drawer/sheet atau compact navigation yang eksplisit; jangan memadatkan sidebar 260 px menjadi 90 px hingga label tidak terbaca.
- Metrik bisa 1 atau 2 kolom sesuai lebar; label uang harus terbaca tanpa clipping.
- Chart harus tetap punya label penting; gunakan ringkasan yang lebih ringkas daripada shrink chart hingga tidak terbaca.

## 10. F12 — Pesanan Masuk (UC-34) dan Invoice (UC-35)

### Halaman Pesanan Masuk

Gunakan struktur skenario UC-34 sebagai basis data table:
- **Nomor Pesanan**.
- **Tanggal**.
- **Judul Buku**.
- **Jumlah Beli**.
- **Pendapatan Bersih**.
- **Status Lunas**.
- Aksi terkait invoice pada pesanan yang memenuhi syarat.

Rekomendasi UX:
- Judul halaman `Pesanan Masuk`, deskripsi singkat hanya bila diperlukan.
- Search/filter yang memang membantu: cari pesanan atau periode; jangan tambahkan 8 filter yang tidak dibutuhkan.
- Posisikan status dalam satu kolom, jangan mengulangnya lewat badge di banyak tempat.
- Gunakan row actions yang mudah dipahami, bukan ikon ellipsis tanpa label ketika hanya ada satu tindakan.
- Tampilkan jumlah hasil atau pagination **jika kumpulan demo memang memerlukannya**, bukan angka hias.
- Empty state: `Belum ada pesanan masuk` tanpa CTA yang tidak relevan.
- Jika perlu data satu pesanan dengan beberapa buku, pastikan formatnya tidak menduplikasi order ID tanpa penjelasan; bisa gunakan ringkasan per order dan detail contextual, namun jangan mengarang aturan backend.

### Invoice Access

- Untuk pesanan lunas, tampilkan tindakan `Unduh Invoice` atau `Lihat Invoice` sesuai alur desain.
- Figma prototype hanya **mensimulasikan** feedback/preview; tidak mengunduh berkas nyata.
- Sertakan state `Gagal menyiapkan invoice` dan aksi mencoba lagi bila sesuai kebutuhan skenario.
- Bila membuat pratinjau invoice sebagai specimen, tampilkan identitas transaksi yang sama dengan tabel; jangan membuat invoice dengan biaya, pajak, atau komisi yang tidak ditentukan dokumen.
- Jangan membuat invoice pembeli (itu konteks fitur lain); ini perspektif **penjualan milik penerbit**.

### Responsiveness

- Desktop menggunakan data table yang tertata.
- Mobile jangan mengecilkan tabel 6–7 kolom sampai tak terbaca. Gunakan row summary/list dengan detail on demand, atau horizontal scroll yang sengaja dirancang jika tepat; pilih berdasarkan keterbacaan.

## 13. Admin specimen — Kelola Pengguna & Verifikasi Penerbit (skenario UC-40)

Ini **master screen yang cukup representatif**, bukan implementasi semua kemungkinan administrasi.

### List view

- Tampilkan pembeli dan penerbit secara jelas; jangan menyatukan dua tipe aktor tanpa label yang relevan.
- Kolom yang beralasan: nama/identitas, peran, status akun, tanggal daftar bila didukung data demo, serta aksi relevan.
- Penyaringan berdasarkan peran dan status boleh ada karena membantu tugas verifikasi; jangan menampilkan filter yang tidak dipakai.
- Status yang perlu dibedakan di contoh data: menunggu verifikasi, aktif, nonaktif; ditolak jika skenario penolakan diperlihatkan.

### Publisher application review

- Buat contoh **detail pengajuan penerbit**, dengan data yang sesuai form pendaftaran yang dijelaskan dokumen, bukan dokumen/legal fields rekaan.
- Keputusan `Setujui Penerbit` dan `Tolak Pendaftaran` harus mempunyai alasan dan feedback yang jelas; untuk penolakan, skenario mensyaratkan alasan.
- Tampilkan minimal specimen state: `Menunggu Verifikasi`, `Disetujui`, dan `Ditolak + alasan` bila dibuat.
- Representasikan `Aktifkan/Nonaktifkan Akun` secara hati-hati, misalnya contextual confirm dialog, tanpa destructive action tanpa kejelasan.
- Jangan membuat email pengiriman nyata, audit log backend, atau database updates; hanya gambarkan feedback prototyping.

### Interactions

- List → detail review.
- Detail → confirm approve atau rejection reason specimen.
- Success/error/confirmation hanya bila benar-benar digunakan untuk menjelaskan interaksi.
- Jangan buat 12 modal terpisah untuk tiap variasi kecil.

## 14. Admin specimen — Pengawasan Katalog Global (skenario UC-41)

### List view

### Moderation specimen

## 15. Images, brand, dan asset reuse

Fase ini lebih berorientasi pada data. **Jangan menambahkan foto demi mengisi ruang kosong.** Gambar diperlukan hanya ketika meningkatkan pengenalan entitas.

Prioritas:
1. Reuse aset sampul buku yang sudah masuk `01 — Assets` dari Phase 01.
2. Jika ada buku baru yang benar-benar diperlukan, cari sumber resmi/berizin, catat asalnya, dan gunakan proses import aset melalui kemampuan Figma MCP yang tersedia (misalnya `upload_assets` bila tersedia).
3. Gunakan logo resmi IKAPI/penerbit jika sudah tersedia dan izin jelas; jangan membuat brand palsu. Untuk contoh penerbit, wordmark teks netral dan data demo lebih aman daripada logo palsu.

Jika `upload_assets` tidak tersedia atau gagal, jangan mengklaim aset baru berhasil dimasukkan. Gunakan aset yang sudah ada secara sah atau laporkan batasnya.

## 16. Hard anti-AI-slop rules (berlaku untuk semua frame)

### Copywriting

- Bahasa Indonesia natural, profesional, ringkas, jelas, dan tidak kaku.
- Larang slogan cringe seperti `Pantau kesuksesan penerbitanmu!`, `Jelajahi insight tanpa batas!`, `Perjalanan literasi yang luar biasa`, `Yeay`, `Oopsie`, `Maksimalkan potensimu`, `Semua dalam genggaman`, atau *motivational filler*.
- Label yang lebih sesuai: `Dashboard`, `Pesanan Masuk`, `Pendapatan Bersih`, `Saldo Tersedia`, `Kelola Pengguna`, `Verifikasi Penerbit`, `Katalog Global`, `Belum ada pesanan masuk`.
- Jangan mengulangi judul halaman dalam eyebrow, headline, subtitle, card heading dan badge secara berlapis.
- Jangan mengulangi angka yang sama di chart, summary card dan panel tambahan tanpa alasan analitis.
- Jangan gunakan lorem ipsum atau microcopy panjang yang tidak membantu keputusan.

### Visual

- **Tidak ada badge, status pills, atau colored dots di setiap card/row**. Gunakan satu penanda status hanya jika menyampaikan keadaan nyata.
- Jangan membuat semua info menjadi card; table/list/grouped section lebih baik ketika informasi sifatnya tabular.
- Tidak ada decorative sparkles, blobs, emoji, gradients, glowing orbs, multi-shadows, glassmorphism, oversized radius, atau fancy charts tanpa data.
- Tidak ada card-within-card bertingkat, 3+ level shadow surfaces, sidebar floating dekoratif, serta header oversized pada dashboard.
- Tidak ada ikon pada setiap label atau setiap row tanpa fungsi.
- Tidak ada empty-state ilustrasi aneh, rocket, confetti, atau mascots.
- Jangan membagi setiap status, tanggal, harga, judul, penerbit, dan tindakan ke enam badge terpisah.
- Gunakan whitespace secukupnya; UI operasional perlu **information density yang nyaman**, bukan terlalu lega atau terlalu sesak.
- Chart sederhana, readable dan akurat lebih baik daripada chart kompleks dengan filler warna-warni.

### Functional judgment

- Badge/status label **boleh** ketika status akun, pembayaran, atau buku akan ambigu tanpanya; jangan menandai semua teks sebagai status.
- Pill/chip **boleh** untuk filter interaktif yang memang dipakai, tidak sebagai dekorasi.
- Shadow **boleh** untuk dialog/popover yang membutuhkan depth ringan, bukan pada semua card.
- Konfirmasi **wajib masuk akal** untuk tindakan admin sensitif, tapi hindari modal untuk setiap aksi non-destruktif.
- Setiap elemen harus punya fungsi UX yang dapat disebutkan. Jika tidak, hapus.

Setelah setiap batch frame, lakukan audit desain dan hapus elemen redundan. **Jangan menambah ornamen hanya karena tampilan terasa kosong**; perbaiki struktur, tipografi, dan data lebih dahulu.

## 18. Production-quality layout behavior, accessibility, dan data clarity

- Desktop reference frame: **1440 px**. Mobile reference frame: **390 px**. Pertahankan konvensi Phase 01 bila frame existing menggunakan ukuran setara.
- Tablet: pertimbangkan perubahan grid/sidebar melalui constraints, tidak wajib menggambar semua breakpoint jika tidak bernilai.
- Sidebar operational harus mempunyai state aktif yang jelas dan visual hierarchy yang stabil antarhalaman.
- Detail data table pada desktop jangan memaksa content tersebar sepanjang 1440 px tanpa keterbacaan.
- Desain mobile harus *purposefully adapted*; jangan cuma scale turun semua elemen desktop.
- Gunakan Auto Layout pada shell/sidebar, topbar, cards, controls, table rows, dialogs, chart container dan major sections.
- Gunakan constraints/resizing masuk akal, hindari fixed layers yang overlap atau clip ketika parent diubah.
- Pastikan label action jelas, target sentuh mobile memadai, focus/selected states bisa dikenali, status tidak hanya dibedakan oleh warna.
- Pastikan chart, angka rupiah, tanggal, nomor order, nama panjang penerbit, dan judul buku tidak overflow.
- Jangan memakai chart mockup sebagai satu image; harus native editable layers.
- Lakukan pemeriksaan screenshot/visual bila MCP mendukung inspeksi. Jangan menyatakan sudah QA visual bila hanya membaca daftar node.
