## 4. Architecture — Modular Monolith

Gunakan pola **modular monolith**, bukan microservices.

Arsitektur utama:

```
Browser
   |
   v
Laravel Application
   |
   +-- Inertia.js
   |      |
   |      +-- React + TypeScript
   |      +-- Tailwind CSS
   |      +-- shadcn/ui
   |
   +-- Routing / Controllers
   +-- Authentication / Authorization
   +-- Domain Modules
   +-- Eloquent ORM
   +-- Queue Infrastructure
   |
   v
PostgreSQL
```

Prinsip arsitektur:

1. Gunakan satu aplikasi Laravel untuk frontend web dan backend.
2. React menggunakan Inertia sebagai integrasi dengan Laravel.
3. Jangan membuat REST API terpisah untuk semua halaman tanpa kebutuhan yang jelas.
4. Pisahkan modul berdasarkan domain bisnis.
5. Pertahankan konvensi Laravel dan struktur resmi starter kit.
6. Jangan menerapkan Clean Architecture, DDD, CQRS, Event Sourcing, atau repository abstraction secara berlebihan.
7. Jangan membuat generic service, manager, helper, atau abstraction layer yang belum memiliki kebutuhan.
8. Jangan menghapus fitur bawaan framework hanya demi menerapkan struktur buatan sendiri.

Tujuannya adalah menjaga codebase mudah dipahami dan dikembangkan, bukan menciptakan arsitektur yang terlalu rumit.

Sebutkan dokumen yang berhasil dibaca dan ringkas pemahaman arsitektur yang digunakan untuk scaffolding.

### B. Technical Stack Installed

Tampilkan teknologi, versi aktual, dan status instalasinya.

Bedakan dengan jelas:

- Installed &amp; configured
- Installed but not fully verified
- Planned for future implementation
- Blocked / incompatible

### C. Project Structure

Tampilkan struktur direktori utama yang benar-benar dibuat, bukan sekadar struktur usulan.

### D. Configuration

Jelaskan konfigurasi development, database, environment, dan tooling yang telah disiapkan.

### E. Verification Results

Sebutkan perintah yang benar-benar dijalankan beserta hasilnya.

Jangan mengklaim build, tests, atau database connection berhasil jika belum dijalankan atau hasilnya gagal.

### F. Outstanding Issues

Laporkan dependency yang belum kompatibel, konfigurasi yang belum tersedia, atau kendala environment yang memerlukan tindak lanjut.

### G. Final Checklist

Centang hanya pekerjaan yang telah selesai dan diverifikasi.

### H. Next Phase Readiness

Nyatakan apakah project sudah siap memasuki fase **Frontend Interactive Prototype menggunakan mock data**.

Jangan memulai fase tersebut.

## 15. Definition of Done

Task baru dianggap selesai ketika:

1. Seluruh dokumentasi yang tersedia sudah ditinjau dan hasilnya dipahami.
2. Project foundation sudah dibuat menggunakan tech stack yang ditentukan.
3. Struktur folder sudah sesuai kebutuhan arsitektur dan tidak overengineered.
4. Konfigurasi development dan quality tooling sudah disiapkan.
5. Pemeriksaan teknis yang memungkinkan sudah dijalankan dan hasilnya dilaporkan.
6. Tidak ada integrasi production atau implementasi fitur bisnis yang dilakukan di luar scope.
7. README dan laporan akhir menjelaskan kondisi aktual repository.

**Final instruction:**

Kerjakan hanya **Phase 1 — Project Initialization &amp; Scaffolding**.

Jangan meneruskan pekerjaan menjadi pembuatan prototype, dashboard, katalog, checkout, atau implementasi fitur lainnya.

Target akhirnya adalah **repository yang secara teknis siap dikembangkan**, bukan marketplace yang sudah jadi.

Ketika scaffolding selesai, hentikan pekerjaan dan laporkan hasilnya secara lengkap.
