## 1. OBJECTIVE

Implementasikan pengelolaan profil instansi penerbit dan rekening bank penerima pencairan menggunakan backend serta database asli.

Fitur harus memungkinkan penerbit yang sudah terautentikasi dan memiliki hak akses untuk:

- Melihat data instansi yang tersimpan.
- Memperbarui informasi instansi yang diperbolehkan.
- Melihat rekening bank penerima pencairan.
- Menambahkan rekening bila belum tersedia.
- Mengubah informasi rekening.
- Menyembunyikan/menampilkan nomor rekening secara aman.
- Membatalkan edit.
- Menyimpan perubahan setelah validasi backend.
- Mendapat feedback yang jelas.
- Melihat informasi terbaru setelah refresh.

Ini adalah pengembangan website sebenarnya. Jangan menggunakan localStorage sebagai database.

**Jangan membuat sistem pendaftaran penerbit baru.** Gunakan identitas dan data yang sudah disediakan Fadli UC-28/29.

## 3. SCOPE BERDASARKAN UC-30

Skenario resmi menetapkan:

1. Sistem menampilkan profil penerbit dan rekening yang tersimpan.
2. Penerbit mengubah data profil atau rekening.
3. Rekening terdiri dari nama bank, nomor rekening, dan nama pemilik.
4. Penerbit menekan `Simpan Pengaturan`.
5. Backend memvalidasi data.
6. Sistem menyimpan perubahan.
7. Sistem menampilkan informasi terbaru.
8. Pada input tidak valid, perubahan dibatalkan dan data tersimpan dipertahankan.

Gunakan data instansi dari registrasi UC-28, misalnya:

- Nama penerbit.
- Penanggung jawab.
- Email kontak.
- Nomor telepon.
- Alamat.
- Nomor anggota IKAPI.

Jangan menduplikasi field bila sudah ada dalam publisher registration/profile model.

Pastikan ownership setiap field jelas. Contohnya, email autentikasi User tidak otomatis sama dengan email kontak penerbit bila model bisnis memisahkannya.

## 4. DATA ARCHITECTURE

Gunakan satu sumber identitas dan satu sumber profil instansi.

```
Authenticated User
       |
       v
Authorized Publisher
       |
       +-- Institution Profile
       |      - Publisher Name
       |      - Responsible Person
       |      - IKAPI Member Number
       |      - Contact & Address
       |
       +-- Payout Bank Account
              - Bank Name/Code
              - Account Number
              - Account Holder
```

Ini diagram konseptual, bukan perintah membuat semua model baru.

### Database rules

- Reuse relasi User dan Publisher yang dibuat Fadli.
- Gunakan migration baru jika skema perlu diperluas.
- Jangan menulis ulang initial migration yang telah digunakan.
- Jangan membuat dua `publishers` table.
- Jangan membuat `bank_accounts` kedua jika existing schema sudah mendukungnya.
- Gunakan foreign key dan constraints yang tepat.
- Jika requirement hanya membutuhkan satu rekening tujuan aktif, jangan membuat multi-rekening management tanpa dasar.
- Jangan menghapus rekening lama secara destruktif ketika perubahan sedang gagal.
- Pastikan data lama tetap kompatibel.

### Rekening bank

Nomor rekening adalah identifier, bukan angka untuk perhitungan.

Gunakan string dan pertahankan leading zeros.

Validasi format sesuai aturan bank atau spesifikasi yang benar-benar tersedia. Jangan mengarang satu panjang nomor yang dianggap valid untuk semua bank.

Periksa keamanan penyimpanan data rekening, pertimbangkan enkripsi at-rest melalui mekanisme Laravel bila sesuai desain, serta dokumentasikan konsekuensinya terhadap pembacaan/masking.

Jangan pernah log nomor rekening lengkap secara sembarangan.

**Penting:** UC-30 tidak mengharuskan verifikasi kepemilikan rekening oleh bank. Jangan menampilkan status `Rekening Terverifikasi` hanya karena data berhasil disimpan.

## 5. AUTHORIZATION &amp; ACCOUNT STATUS

Hanya penerbit yang berwenang boleh mengakses halaman ini.

Enforce di backend:

- Pengguna telah login.
- Identitas penerbit valid.
- Approval sesuai kontrak Fadli/Devina.
- Account status mengizinkan akses.
- Publisher hanya dapat mengubah profil dan rekening miliknya.

Jangan menerima publisher ID dari frontend sebagai sumber identitas tepercaya.

Uji manipulasi route parameter.

Jangan berasumsi menyembunyikan tombol pada frontend sama dengan authorization.

Gunakan Policies/Gates sesuai pola repository.

## 6. BACKEND UPDATE BEHAVIOR

Implementasikan endpoint/update flow sesuai Laravel + Inertia conventions.

Pisahkan validasi input dan persistence dari rendering React.

Requirements:

- Data profil tervalidasi server-side.
- Data rekening tervalidasi server-side.
- Perubahan tidak boleh mengubah role, approval, permission, atau status akun.
- Save berhasil menampilkan data terbaru.
- Save gagal tidak mengganti data tersimpan.
- Error field ditampilkan jelas.
- Tidak ada duplicate toast.
- Cancel tidak mengirim perubahan.
- Request dari user lain ditolak.

Jika profil dan rekening mempunyai tindakan Simpan terpisah, gunakan operasi yang independen dan jelas.

Jika menggunakan satu form, pastikan kegagalan validasi tidak menghasilkan penyimpanan parsial.

Jangan membuat sistem audit generik tanpa kebutuhan. Namun perubahan data rekening yang penting perlu memiliki pencatatan yang memadai jika pola audit sudah tersedia.

### Integrasi pencairan

UC-36 nantinya membutuhkan rekening tujuan.

Jika rekening diubah saat sudah ada pengajuan pencairan berjalan, pengajuan lama tidak boleh diam-diam berpindah ke rekening baru.

Dokumentasikan kebutuhan **snapshot rekening tujuan pada saat pengajuan** untuk Prompt 06.

Jangan membangun sistem payout sekarang.

Struktur di atas adalah wireframe konseptual, bukan data hardcoded.

### Important UX rules

- View mode menampilkan informasi normal, bukan semua field disabled.
- Edit mode menampilkan input serta Simpan/Batal.
- Mask nomor rekening pada tampilan awal.
- Reveal/hide dilakukan secara sengaja.
- Jangan mengisi bagian nomor rekening kosong dengan informasi bank dummy.
- Bila rekening belum didaftarkan, tampilkan empty state dan CTA `Tambah Rekening`.
- Jangan mencampur data instansi dan rekening dalam satu daftar panjang tanpa grouping.
- Dua section boleh digunakan, tetapi hindari dua giant cards dengan card nesting berlebihan.
- Jangan tampilkan `Batasan Integrasi F02 ke F14` atau note arsitektur serupa.
- Jangan menampilkan kode UC, nama PIC, atau penjelasan backend di halaman.

### Strict anti-AI-slop

Dilarang:

- Status pill berlebihan.
- Decorative dots.
- Giant shadows.
- Glow/gradients.
- Fake verification seals.
- Statistik penerbit yang tidak dibutuhkan.
- Background putih pada setiap teks.
- Copywriting motivasional.
- Paragraf teknis berulang.
- Ikon hanya untuk dekorasi.

Gunakan bahasa Indonesia natural dan desain Notion-inspired yang sudah ditetapkan.

## 10. TESTING

Uji minimal:

1. Guest tidak dapat membuka/menyimpan profil.
2. Buyer tidak dapat membuka pengaturan penerbit.
3. Penerbit pending/suspended ditangani menurut policy.
4. Approved publisher dapat melihat data sendiri.
5. Publisher A tidak dapat mengubah Publisher B.
6. Data profil tersimpan.
7. Data rekening tersimpan.
8. Nomor rekening dengan leading zero tetap utuh.
9. Rekening invalid ditolak.
10. Save gagal mempertahankan data lama.
11. Masking/reveal sesuai UI.
12. Change rekening tidak memodifikasi status approval.
13. Role/permission tidak bisa ditimpa lewat request.
14. Data baru tersedia setelah refresh.
15. Tidak ada notification ganda.
16. Existing Fadli authentication tetap berjalan.
17. Tidak ada perubahan pada payout existing.

Jalankan test menggunakan PostgreSQL test database terisolasi.
