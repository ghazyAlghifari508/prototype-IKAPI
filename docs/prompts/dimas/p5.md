# TASK 05 — IKAPI Jawa Barat: Balasan Resmi Penerbit pada Komentar dan Ulasan Buku

**Target:** Website IKAPI sebenarnya, bukan prototype.

## 1. PRIMARY OBJECTIVE

Implementasikan kemampuan penerbit memberikan tanggapan resmi terhadap komentar dan ulasan pembeli pada buku yang dikelolanya.

Berdasarkan UC-38:

1. Penerbit membuka ulasan pada buku miliknya.
2. Penerbit memilih `Balas Komentar`.
3. Penerbit menulis tanggapan.
4. Penerbit menekan `Kirim Balasan`.
5. Backend memvalidasi isi.
6. Balasan disimpan ke database.
7. Balasan diidentifikasi sebagai tanggapan penerbit.
8. Balasan tampil di bawah ulasan pembeli.
9. Jika kosong, input ditolak dan teks dapat diperbaiki.

**Jangan membuat sistem komentar/ulasan pembeli dari nol.** Fitur tersebut milik Falih (UC-07 dan UC-20).

## 3. DATA &amp; RELATIONSHIP

Balasan harus terhubung ke ulasan yang tepat.

```
Book
  |
  +-- Publisher Owner
  |
  +-- Buyer Review
          |
          +-- Review Content
          +-- Reviewer
          +-- Review Status
          |
          +-- Publisher Reply
                  |
                  +-- Author Publisher
                  +-- Reply Content
                  +-- Created At
```

Ini diagram konsep, bukan instruksi membuat seluruh model baru.

Gunakan:

- Existing Book ID.
- Existing Review/Comment ID.
- Authenticated publisher.
- Canonical publisher identity.

Jangan membuat `comments` table kedua.

Jika existing model menggunakan polymorphic comments atau relations tertentu, gunakan pattern tersebut.

Jangan membuat general-purpose social network thread engine.

## 4. AUTHORIZATION

Hanya penerbit pemilik buku yang boleh membalas ulasan buku tersebut.

Wajib backend check:

1. Publisher authenticated.
2. Publisher approved dan active sesuai contract.
3. Review valid.
4. Review memang terkait buku yang dimaksud.
5. Buku dimiliki publisher tersebut.
6. Reply action diperbolehkan menurut status review/moderation.
7. Input valid.

Penerbit A tidak boleh membalas ulasan buku penerbit B.

Jangan mengandalkan `publisher_id` dari form sebagai identitas terpercaya.

Gunakan Laravel Policy/Gate.

## 5. OFFICIAL PUBLISHER LABEL

UC-38 mengharuskan balasan ditandai sebagai balasan resmi penerbit.

Artinya:

- Author berasal dari akun penerbit yang benar-benar memiliki buku.
- Balasan terkait publisher identity yang valid.
- UI menunjukkan `Balasan Penerbit`.

Jangan menampilkan:

- Fake certified publisher badge.
- Blue verification check yang tidak ada dasar.
- `Official IKAPI Verified` tanpa kebijakan resmi.
- Role status dari input client.

Identitas resmi berasal dari authorization backend, bukan dari badge yang dapat dipilih pengguna.

## 6. FORM VALIDATION

Validasi backend:

- Teks balasan wajib.
- Whitespace-only tidak diterima.
- Ukuran/panjang teks mengikuti aturan yang didukung spesifikasi dan kebutuhan storage.
- Input tidak dapat mengubah author/publisher/review ownership.
- Content ditampilkan dengan escaping yang aman.
- Jangan mengizinkan script/HTML berbahaya ditampilkan.
- Jika rich text memang tidak diperlukan, gunakan plain text.

Jangan menyimpan konten HTML mentah lalu merendernya tanpa sanitization.

### Empty reply

Pesan:

**"Balasan komentar tidak boleh kosong."**

Pertahankan textarea agar penerbit dapat memperbaiki input.

Jangan membuat modal error besar hanya untuk input kosong.

### Duplicate submission

Cegah double submit yang tidak disengaja.

Jangan membuat duplicate reply hanya karena:

- Double click.
- Loading lambat.
- Page refresh.
- Repeated request.

Gunakan mekanisme sesuai struktur dan aturan reply yang telah disepakati.

Jangan secara sepihak melarang lebih dari satu balasan jika kontrak review yang valid memang memperbolehkan percakapan lanjutan.

## 7. MODERATION BOUNDARY

Dokumen pembagian terbaru memberikan tanggung jawab moderasi kepada Lydia, tetapi nomor use case pada dokumen skenario memiliki ketidaksesuaian.

Jangan mengimplementasikan moderator UI dalam tugas ini.

Periksa kebijakan review yang sudah ada.

- Ikuti kontrak tersebut.
- Jangan langsung mempublikasikan konten yang semestinya pending review.

Jika tidak ada workflow moderasi dan skenario UC-38 mengizinkan publikasi langsung:

- Ikuti perilaku yang sudah disepakati.
- Jangan mengarang proses approval baru.

Catat perbedaan spesifikasi bila ditemukan.

## 8. FRONTEND — PUBLISHER REVIEW REPLY

Gunakan existing React/Inertia publisher layout.

Idealnya balasan terhubung pada halaman ulasan yang sudah tersedia.

Jangan membangun sistem manajemen review lengkap kedua.

### Recommended interaction

```
ULASAN BUKU

Buku: Judul Buku

Pembeli
"Isi komentar atau ulasan pembeli..."

Tanggal ulasan

[Balas Komentar]

------------------------------------

Balasan Penerbit

[ Tulis tanggapan...                 ]
[                                    ]

                     [Kirim Balasan]
```

Setelah save:

```
Pembeli
"Isi komentar pembeli..."

   Balasan Penerbit
   "Terima kasih atas masukannya."
```

Gunakan data yang benar-benar tersedia.

Jangan mengisi balasan produksi dengan dummy text.

### UX requirements

- Review pembeli tetap terbaca.
- Balasan terlihat sebagai bagian dari thread.
- Author jelas.
- Input mudah ditemukan.
- Loading dan success states sesuai.
- Tidak ada duplicate notification.
- Tidak ada cards berlapis berlebihan.
- Tidak ada giant shadows.
- Jangan menambahkan status pill pada tiap komentar.
- Responsive layout.
- Mobile textarea usable.

Jangan menggunakan copywriting seperti:  
"Bangun hubungan penuh keajaiban bersama pembaca!"

Gunakan bahasa normal, contohnya:  
`Balas Ulasan`, `Kirim Balasan`, `Balasan berhasil dipublikasikan`.
