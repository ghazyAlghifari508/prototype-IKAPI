## Critical invariant

Untuk transaksi yang benar-benar dapat dibayar:

```
Canonical Order Payable Total
               =
Midtrans Transaction Gross Amount
```

Jika invoice menyajikan total yang dibayar, angka tersebut juga harus konsisten dengan data transaksi yang sah.

Jangan melakukan penghitungan uang terpisah pada:

- Cart UI.

Gunakan integer/exact numeric arithmetic.

Jangan menggunakan floating-point untuk amount.

# 7. MIDTRANS SECURITY REVIEW

Audit seluruh boundary.

## Secrets

Pastikan:

- Server Key tidak berada di frontend.
- Server Key tidak masuk bundle JavaScript.
- Server Key tidak masuk Inertia props.
- Server Key tidak dicetak di logs.
- `.env` tidak ter-commit.
- Sandbox/Production configuration terpisah.
- Tidak ada hardcoded credential.

## Webhook

Pastikan:

- Endpoint menerima request Midtrans dengan benar.
- CSRF exception terbatas jika diperlukan.
- Signature verification benar.
- Order reference divalidasi.
- Amount divalidasi.
- Currency divalidasi.
- Status provider divalidasi.
- Tidak ada parameter client yang dapat menandai paid.
- Duplicate requests aman.
- Out-of-order notifications aman.
- Failed processing menghasilkan error/retry yang benar.

## Provider status

Pastikan:

- Pending bukan paid.
- Capture diproses berdasarkan fraud/provider conditions.
- Settlement diproses benar.
- Deny/cancel/expire dibedakan.
- Refund/chargeback tidak otomatis dihapus dari histori.
- Browser onSuccess bukan bukti final.
- Browser onClose bukan cancellation.

# 8. IDEMPOTENCY &amp; CONCURRENCY REVIEW

Payment systems harus tahan terhadap repeated execution.

Audit:

- Double CreateOrder.
- Double Snap token creation.
- Double checkout submission.
- Duplicate webhook.
- Repeated settlement.
- Out-of-order pending after settlement.
- Concurrent entitlement grant.
- Concurrent cancellation and settlement.
- Concurrent expiry and settlement.
- Repeated cart restoration.
- Repeated reminder job.
- Reconciliation job overlap.

## Required invariants

```
One verified successful transaction
        |
        v
One effective paid transition
        |
        v
One set of book entitlements
```

Dan:

```
One cancelled/expired order
        |
        v
One effective cart restoration
```

Jangan hanya mengandalkan boolean frontend.

Gunakan database constraints, transactions, row locks, conditional updates, dan event deduplication sesuai arsitektur.

Jika external network call diperlukan, jangan menahan database lock terlalu lama selama operasi jaringan.

# 9. FAILURE RECOVERY

Uji sistem ketika:

- Snap token creation timeout.
- Midtrans mengembalikan error.
- Webhook terlambat.
- Webhook hilang.
- Backend restart.
- Queue worker berhenti.
- Database sementara unavailable.
- Entitlement job gagal.
- Payment sudah sukses tetapi user menutup browser.
- User membuka status dari perangkat berbeda.
- Reminder job terlambat.
- Order melewati deadline saat server down.

## Recovery principles

- Jangan menandai unpaid order sebagai paid.
- Jangan kehilangan paid transaction yang telah diverifikasi.
- Jangan memberikan entitlement dua kali.
- Jangan menandai akses aktif sebelum tersedia.
- Gunakan retry-safe reconciliation.
- Catat failure yang perlu ditangani.
- Jangan menampilkan misleading success.
- Jangan membuat silent state corruption.

## Reconciliation

Periksa mekanisme pengecekan transaksi ke Midtrans Get Status API.

Gunakan secara terkontrol:

- Saat webhook diragukan.
- Saat status local kemungkinan stale.
- Saat recovering missing notifications.
- Saat status page memerlukan refresh terotorisasi.

Jangan menjalankan polling berlebihan untuk semua transaksi.

Jangan mengubah status hanya berdasarkan deadline browser.
