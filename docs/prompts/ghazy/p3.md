# 7. PAYMENT ATTEMPT MANAGEMENT

- Pembayaran pending.
- Provider error.
- Retry.
- Expiry.

## Recommended contract

Pisahkan:

**Business Order**

- Identitas pembelian.
- Buyer.
- Item snapshots.
- Total.
- Business status.

**Provider Payment Attempt**

- Referensi transaksi provider.
- Provider order identifier.
- Snap token reference jika sesuai.
- Requested channel.
- Confirmed payment type.
- Provider status.
- Timestamps.
- Expiration.

## Important retry rule

Midtrans mempunyai aturan identifier transaksi.

Jangan menggunakan ulang provider order ID yang sudah memiliki transaksi incompatible lalu memaksa create token baru.

Periksa:

- Kapan Snap token existing bisa dipakai kembali.
- Kapan payment attempt baru diperlukan.
- Bagaimana order bisnis tetap sama tetapi provider attempt tetap unik.
- Bagaimana expired/cancelled attempt ditangani.
- Bagaimana status attempt lama tidak dapat mengubah order secara keliru.

Jangan menganggap menutup popup berarti payment attempt berakhir.

- Tampilkan status menunggu sesuai backend.

`onError`:

- Tampilkan masalah pembayaran dan opsi aman.

`onClose`:

- Jangan otomatis membatalkan order.

- Tetap tampilkan informasi pesanan.

# 9. MIDTRANS WEBHOOK

Buat atau reuse webhook endpoint yang khusus menangani notification Midtrans.

Webhook berasal dari server provider, bukan user browser.

## Security boundary

Webhook:

- Tidak memerlukan session browser.
- Tidak bergantung pada CSRF token browser.
- Harus memverifikasi autentisitas provider.
- Harus memvalidasi payload.
- Harus mengidentifikasi transaksi yang benar.
- Tidak boleh memberikan akses kepada request palsu.

Jika Laravel memerlukan pengecualian CSRF untuk webhook, buat pengecualian yang **spesifik terhadap route webhook tersebut** berdasarkan dokumentasi Laravel 13.

Jangan menonaktifkan perlindungan CSRF untuk seluruh aplikasi.

Jangan mengganti verifikasi provider dengan pemeriksaan `User-Agent`.

## Signature verification

Untuk notification Midtrans yang memakai `signature_key`, dokumentasi menyebut:

```
SHA512(order_id + status_code + gross_amount + ServerKey)
```

Gunakan nilai dan representasi string sesuai kontrak provider.

Bandingkan secara aman, misalnya memakai fungsi perbandingan constant-time yang sesuai.

Jangan menggunakan floating-point conversion yang mengubah representasi `gross_amount` sebelum signature diverifikasi.

Jangan menganggap signature valid cukup tanpa memeriksa transaksi yang direferensikan benar.

# 11. PAYMENT STATUS MAPPING

Midtrans menggunakan beberapa status provider.

Minimal pahami:

- `pending`
- `capture`
- `settlement`
- `deny`
- `cancel`
- `expire`
- `failure`
- `refund`
- `partial_refund`
- `chargeback`

Tidak semuanya boleh langsung dipetakan ke dua boolean:

`is_paid` / `is_failed`.

## Successful payment

Dokumentasi Midtrans mengizinkan interpretasi transaksi kartu `capture` sebagai keberhasilan dalam kondisi yang sesuai.

Namun harus memperhatikan status fraud/authorization dan aturan provider.

Untuk sebagian besar transaksi asinkron, `settlement` merupakan indikasi pembayaran berhasil.

**Jangan menganggap setiap** `capture` **sukses tanpa memeriksa kondisi yang diwajibkan provider.**

Jangan menganggap `authorize` sebagai pembayaran lunas bila merchant tidak menggunakan alur pre-authorization yang sesuai.

## Refund/chargeback

Refund dan chargeback memiliki konsekuensi bisnis sendiri.

Jangan langsung menghapus entitlement pembeli atau mengubah publisher ledger tanpa kebijakan yang telah disepakati.

Catat sebagai state/event yang memerlukan penanganan sesuai kontrak bisnis.

Jangan mengarang kebijakan refund.

# 12. IDEMPOTENCY &amp; OUT-OF-ORDER EVENTS

Midtrans dapat mengirim:

- Notification berulang.
- Notification terlambat.
- Notification tidak berurutan.

Contoh:

```
Webhook 1: settlement
Webhook 2: settlement
Webhook 3: pending (terlambat)
```

Hasil:

```
Order tetap PAID
Entitlement hanya diberikan sekali
Tidak ada status mundur ke pending
Tidak ada pendapatan dicatat dua kali
```

## Required behavior

- Idempotent webhook processing.
- Unique provider identifiers.
- Atomic state transitions.
- Row locking/conditional writes sesuai kebutuhan.
- Dedupe events jika data yang diperlukan tersedia.
- State regression prevention.
- Tidak mengulang fulfillment ketika duplicate success.
- Retry-safe error handling.
- Fast acknowledgment sesuai rekomendasi provider.

Jangan menaruh operasi network eksternal di dalam transaksi database panjang tanpa alasan.

Pisahkan provider verification dan database mutation dengan konsistensi yang benar.

# 13. ENTITLEMENT FULFILLMENT

UC-13 secara eksplisit meminta hak akses e-book aktif setelah pembayaran terverifikasi.

Gunakan canonical entitlement contract yang disepakati dengan Devina dan Falih.

## Expected flow

```
Verified Successful Payment
             |
             v
Canonical Order Paid Transition
             |
             v
Load Order Items
             |
             v
Grant Book Entitlements
             |
             v
Publisher Sales/Earning Event
(if financial contract exists)
             |
             v
Personal Library Can Read Ownership
```

## Grant once

Pembeli harus mendapat hak akses ke seluruh buku yang sah dalam order.

Pastikan:

- Buyer ID benar.
- Book IDs benar.
- Multi-book order ditangani.
- Multi-publisher order ditangani.
- Tidak ada duplicate entitlement.
- Transaction ownership tidak berubah.
- Pembayaran pending tidak memberikan akses.
- Browser callback tidak memberikan akses.

Gunakan database transaction untuk perubahan data yang perlu atomik.

Jika fulfillment asinkron:

- Gunakan queued jobs setelah commit.
- Pastikan retries aman.
- Pastikan order paid tidak dianggap seluruhnya fulfilled sebelum entitlement benar-benar diberikan.
- Tangani kegagalan entitlement secara recoverable.

## Ownership boundary

Ghazy bertanggung jawab memicu dan memastikan grant setelah pembayaran terverifikasi.

Devina bertanggung jawab menyediakan pengalaman Perpustakaan Pribadi.

Falih bertanggung jawab menegakkan entitlement pada Reader.

**Jangan membuat halaman Library atau E-Reader kedua.**

Jika entitlement model belum ada, koordinasikan kontrak minimal bersama domain Library. Jangan membuat tabel duplikat yang membuat ownership tidak sinkron.
