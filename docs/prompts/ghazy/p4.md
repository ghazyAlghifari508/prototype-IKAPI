# 3. UC-15 — PAYMENT STATUS

Skenario menetapkan:

1. Pembeli membuka Status Pembayaran.
2. Sistem membaca status terbaru dari database.
3. Sistem menampilkan:
   - Menunggu Pembayaran.
   - Lunas.
   - Kedaluwarsa.
4. Jika pembayaran melewati masa berlaku, status menjadi Kedaluwarsa dan kode pembayaran tidak lagi berlaku.

## Important distinction

Database adalah sumber status aplikasi, tetapi data harus disinkronkan dengan Midtrans melalui mekanisme terpercaya.

Jangan mengandalkan:

- Status JavaScript.
- Snap popup state.
- Query `status=success`.
- localStorage.
- Countdown browser.

Jika status database kemungkinan stale:

- Gunakan mekanisme reconciliation yang sudah disiapkan.
- Jangan mengirim Get Status API berulang setiap detik.
- Jangan membuat satu transaksi provider baru hanya untuk mengecek status.

# 4. UC-16 — DIGITAL ORDER STATUS

Skenario menyebut:

- Menunggu Pembayaran.
- Lunas.
- Selesai — Hak Akses Buku Aktif.

**Payment verification dan fulfillment bukan hal yang sama.**

Contoh:

```
Order #1001

Payment: Lunas

Book Access:
Sedang Diproses
```

Keadaan tersebut bisa terjadi jika pembayaran telah terverifikasi tetapi pemberian entitlement melalui queue belum selesai.

Jangan menampilkan `Hak Akses Aktif` sebelum entitlement benar-benar tersedia.

## Suggested domain separation

```
Payment Status
    |
    +-- Pending
    +-- Paid
    +-- Failed/Denied
    +-- Cancelled
    +-- Expired
    +-- Refund/Dispute states if supported

Order Fulfillment
    |
    +-- Awaiting Payment
    +-- Processing Entitlements
    +-- Access Active
    +-- Exception/Needs Attention
```

Nama internal harus mengikuti kontrak aktual.

Jangan membuat enum baru hanya karena diagram memberi contoh.

# 5. CANONICAL STATE TRANSITIONS

Gunakan satu transition handler/service untuk seluruh perubahan status.

```
ORDER CREATED
      |
      v
AWAITING PAYMENT
      |
      +-- Verified Success
      |       |
      |       v
      |     PAID
      |       |
      |       v
      |   FULFILLMENT
      |       |
      |       v
      |   ACCESS ACTIVE
      |
      +-- Verified Cancel
      |       |
      |       v
      |   CANCELLED
      |
      +-- Verified Expire
      |       |
      |       v
      |    EXPIRED
      |
      +-- Verified Failure
              |
              v
           FAILED
```

Ini penyederhanaan konseptual.

Perhatikan bahwa provider status dapat memiliki transisi lain seperti `capture → settlement` dan `settlement → refund`.

Jangan mengubah paid order menjadi pending karena webhook lama.

Jangan membuat status terminal lokal yang bertentangan dengan status gateway.

## Reconciliation-first approach

Pada callback terlambat atau kontradiktif:

- Periksa current local state.
- Identifikasi provider attempt yang benar.
- Bila diperlukan, panggil Get Status API.
- Terapkan transition yang valid.
- Catat event.
- Jangan silently override state yang sudah final.

# 6. CANCELLATION — IMPORTANT DISTINCTION

**Menutup popup Snap bukan membatalkan pembayaran.**

Jika pengguna hanya menutup popup:

- Jangan langsung mengubah order menjadi cancelled.
- Jangan langsung restore cart.
- Jangan membuat Snap token baru secara otomatis.
- Pertahankan status pending atau status provider yang benar.

Jika pengguna memilih aksi **Batalkan Pesanan** secara eksplisit:

1. Periksa order ownership.
2. Periksa current status.
3. Periksa attempt provider.
4. Periksa apakah cancellation masih diperbolehkan.
5. Gunakan Midtrans Cancel API jika diperlukan.
6. Verifikasi hasil provider.
7. Terapkan transition dengan aman.
8. Restore cart sesuai kontrak Falih.
9. Tampilkan status cancelled.

Referensi:

[https://docs.midtrans.com/reference/cancel-transaction](https://docs.midtrans.com/reference/cancel-transaction)

## Paid order

Jangan mengizinkan paid/settled order dibatalkan hanya melalui tombol UI.

Pembatalan transaksi sukses berbeda dari proses refund.

Jika refund belum disepakati, jangan membuat automatic refund.

# 7. EXPIRATION — PROVIDER-ALIGNED

Jangan menganggap countdown mencapai nol berarti provider pasti sudah menolak semua channel.

Periksa:

- Deadline aplikasi.
- Midtrans Snap page expiry.
- Actual payment method expiry.
- Provider status.
- Pending payment attempt.

## Expected approach

```
Deadline Reached
       |
       v
Refresh/Reconcile Provider Status
       |
       +-- Paid
       |     |
       |     v
       |   Fulfill
       |
       +-- Still Pending
       |     |
       |     v
       |   Handle Provider Expiry/Cancel
       |   As Allowed
       |
       +-- Expired
             |
             v
       Mark Expired
             |
             v
       Restore Cart
```

Jangan menandai expired secara final jika provider masih dapat menerima pembayaran berdasarkan konfigurasi sebenarnya dan belum disinkronkan.

Gunakan scheduler/job bila sesuai.

Jangan menjalankan polling berat untuk setiap order pada setiap request.

Jika provider tidak memberikan notification tertentu untuk masa berlaku halaman Snap saja, jangan menganggap webhook expiry pasti akan datang.

# 8. CART RESTORATION

UC-13/14 mengharuskan pemulihan buku ke keranjang ketika order batal atau kedaluwarsa.

Gunakan kontrak Falih.

## Requirements

- Restore hanya dari order eligible.
- Restore item yang benar.
- Restore quantity menurut kebijakan yang disepakati.
- Jangan membuat duplicate cart items.
- Jangan restore dua kali karena webhook retry.
- Jangan mengubah order snapshot.
- Jangan restore order yang sudah lunas.
- Jangan memberikan akses buku pada cancelled order.
- Buku yang saat ini unpublished/unavailable perlu ditangani sesuai kebijakan.
- Revalidation harga dilakukan saat checkout ulang.

## Idempotent restore

```
Order CANCELLED

Restore #1 → Item returned
Restore #2 → No duplicate item
Restore #3 → No duplicate item
```

Gunakan unique constraints/idempotency sesuai model Cart yang sudah ada.

Jangan membuat Cart model kedua.

# 9. RETRY PAYMENT

Retry memiliki beberapa kemungkinan.

### Case A — Snap popup ditutup

Transaksi masih pending atau token masih berlaku.

Gunakan Snap token/attempt existing jika valid.

### Case B — Payment attempt gagal

Periksa apakah user boleh membuat attempt baru untuk business order yang sama.

### Case C — Expired/cancelled

Periksa kebijakan order baru dan payment attempt baru.

Jangan menghidupkan kembali identifier provider yang sudah terminal tanpa dukungan resmi.

## Retry requirements

- Tidak membuat duplicate orders.
- Tidak menggunakan payment token expired.
- Tidak menggandakan order items.
- Tidak mengubah harga snapshot tanpa aturan.
- Tidak menggandakan entitlement.
- Tidak mengabaikan payment attempt lama.
- Tidak membuat dua pending attempts yang saling konflik.
- Jangan membuat tombol Retry yang hanya memanggil `window.location.reload()` tanpa tindakan yang benar.

Jika kebijakan retry belum disepakati, gunakan opsi yang aman dan jelaskan batasnya.
