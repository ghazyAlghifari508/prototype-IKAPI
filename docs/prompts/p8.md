# 5. CRITICAL QUALITY REQUIREMENT — VISUAL-FIRST DESIGN

Previous FigCraft outputs demonstrated avoidable visual problems, including:

- White-background containers around ordinary text.
- Excessive unused canvas space.
- Weak visual hierarchy.
- Inconsistent component density.
- Overly small text.
- Misaligned overlays and dialogs.
- UI appearing assembled from arbitrary rectangular elements.
- Insufficient visual inspection before completion.

\*\*These defects must not be repeated in Phase 06.\*\*

## 5.1 Design one primary screen at a time

Do not generate all payment frames in one uncontrolled batch.

For each primary screen:

1. Inspect relevant existing components.
2. Establish the screen's information hierarchy.
3. Build the frame.
4. Render or capture its actual appearance using supported FigCraft tools.
5. Inspect the rendered result.
6. Identify visual and structural issues.
7. Correct the issues.
8. Inspect again.
9. Continue only when the major visual problems are resolved.

## 5.2 White-background prevention

Ordinary text must not automatically receive its own white background container.

Examples:

Incorrect:
- A full-width white rectangle behind the page heading.
- Another white rectangle behind its subtitle.
- A separate white background behind every label.
- Nested white cards containing only a short sentence.

Correct:
- Heading text directly on the existing page canvas.
- Subtitle below the heading without unnecessary fill.
- White surfaces reserved for actual cards, panels, forms, tables, and dialogs.

When a white background appears unnecessarily, inspect the parent container's fill properties.

Correct the actual layer structure instead of placing additional decorative elements over the issue.

## 5.3 Layout composition

Pay attention to:
- Content distribution.
- Parent/child container alignment.
- Balanced spacing.
- Comfortable reading widths.
- Consistent content density.
- Logical grouping.
- Proper responsive constraints.

Do not fill empty space with fabricated content just to make the layout appear busy.

Whitespace is acceptable when intentional, but large accidental blank regions and unfinished compositions are not.

## 5.4 Verification is mandatory

Successful MCP execution does not equal successful design.

Always inspect the rendered result when supported.

Use structural linting as an additional check, not as a replacement for visual judgment.

# 7. STRICT ANTI-AI-SLOP RULES

These rules apply to every screen.

## 7.1 Prohibited patterns

Do not create:

- Decorative status pills everywhere.
- Random colored dots.
- Unnecessary badges.
- Excessive rounded containers.
- Giant shadows.
- Glowing elements.
- Arbitrary gradients.
- Decorative blobs.
- Generic fintech illustrations.
- Oversized success icons.
- Multiple nested cards without purpose.
- Repetitive information sections.
- Redundant action buttons.
- Icons beside every heading.
- Unnecessary step progress indicators.
- Fake urgency banners.
- Decorative line patterns.
- Generic AI-generated dashboard layouts.
- Empty elements added only to occupy space.

## 7.2 Status indicators

Payment states genuinely require recognizable status labels.

Appropriate:
- Menunggu Pembayaran.
- Lunas.
- Dibatalkan.
- Kedaluwarsa.

However:

- One concise status indicator is generally sufficient per relevant information group.
- Do not repeat the same status in multiple badges, banners, and cards.
- Do not rely on color alone.
- Use contextual text when explanation is necessary.

## 7.3 No duplicate information

Avoid:

- Showing the same payable total repeatedly without purpose.
- Repeating the order identifier across every card.
- Displaying identical payment instructions in multiple sections.
- Duplicating the payment status inside headings, badges, callouts, and footers.
- Repeating a success message in a dialog and toast simultaneously.

Payment details should be easy to find without overwhelming the user.

## 7.4 Copywriting quality

Use concise, natural, professional Indonesian.

"Selesaikan Pembayaran"

Bad:
"Oops! Pembayaranmu belum menemukan jalan pulang."

Better:
"Pembayaran belum berhasil."

Bad:
"Waktumu hampir habis! Buruan sebelum kesempatan emas ini menghilang!"

Better:
"Batas waktu pembayaran hampir berakhir."

Bad:
"Selamat! Dunia literasi kini ada dalam genggamanmu!"

Better:
"Pembayaran Berhasil"

Bad:
"Transaksimu sedang diproses oleh sistem ajaib kami."

Better:
"Menunggu konfirmasi pembayaran."

Do not add unnecessary marketing copy to transactional screens.

# 19. RESPONSIVE DESIGN

Follow the established desktop width, approximately 1440px unless the current project uses another standard.

Use layouts appropriate to transactional content.

A two-column arrangement may work for:

- Order summary.

Do not force every screen into a two-column layout.

## Mobile

Follow the existing mobile convention, approximately 390px wide unless established otherwise.

On mobile:
- Preserve readable order details.
- Avoid horizontal overflow.
- Keep amounts visible.
- Keep payment options easy to select.
- Maintain usable buttons.
- Prevent sticky elements from covering important information.
- Keep instructional content readable.
- Avoid overly dense status summaries.

Do not merely shrink the desktop frame.

Provide a credible intermediate layout.

Create explicit tablet frames when necessary to demonstrate meaningful layout changes.

- Long book titles.
- Multiple books in one order.
- Large payment amounts.
- Long payment-method names.
- Expiration dates spanning multiple lines.
- Long instruction text.
- Missing method selection.
- Cancelled and expired states.

# 23. QUALITY GATE — BUILD, SCREENSHOT, CRITIQUE, FIX

This section is mandatory.

Every primary frame must pass a visual quality review before the agent moves to the next main screen.

## 23.1 Build

Create the frame using:
- Existing tokens.
- Existing components.
- Correct data.
- Correct Auto Layout or supported layout primitives.
- Purposeful visual hierarchy.

## 23.2 Screenshot

Capture or render the actual frame using supported FigCraft functionality.

Do not skip this step when a rendering tool is available.

## 23.3 Critique

Inspect the screenshot as a product designer.

Check:
- Does the frame look intentionally designed?
- Is the most important information immediately visible?
- Are any text elements incorrectly surrounded by white fills?
- Is the layout overly empty or overly crowded?
- Are the primary actions clear?
- Are the components appropriately sized?
- Is the text readable at normal viewing size?
- Are shadows, badges, pills, and decorative elements restrained?
- Is any information repeated unnecessarily?
- Does the page look like a trustworthy digital bookstore payment experience?

## 23.4 Fix

Correct detected problems.

Prefer editing existing elements over rebuilding the whole frame.

Examples:
- Remove unnecessary background fills.
- Fix wrong padding.
- Correct Auto Layout alignment.
- Improve text sizes.
- Reduce redundant cards.
- Adjust content width.
- Remove duplicate status indicators.
- Correct awkward line wrapping.
- Improve action hierarchy.
- Fix modal or overlay positions.

## 23.5 Verify again

Render or inspect the updated result.

Continue until significant visual defects are resolved or the actual tool limitation is documented.

Do not stop after one unsuccessful revision.

Do not invent a passing visual QA result.
